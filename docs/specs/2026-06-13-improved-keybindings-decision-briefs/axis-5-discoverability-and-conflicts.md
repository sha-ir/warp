## Axis 5 — Discoverability & truthful conflicts

### A5-Q1 — FLIPPED · _product_ · owner: The Keybindings initiative product DRI decides (user-product-decision), with required sign-off from the Resource Center / docs owner, who owns how much hand-curation (Essentials membership and section ordering) must be preserved as data — and since this option KEEPS that curation rather than deleting it, that sign-off is low-friction. The warpui engine owner is NOT load-bearing for the Phase-1 increment: the resolvability test and the shared app-side builder use the existing get_key_bindings/editable_bindings APIs with no engine change. The engine owner's call is deferred to the separate fixed-binding-identity decision (A5-Q3/Q4) that gates the eventual union.

**Decision.** For catalog-v1, decide how to make the keybindings catalog structurally truthful given that trigger data already comes from ONE live source — the keymap, exposed as editable_bindings() for the settings editor and get_key_bindings() for the resource-center cheatsheet — while the static name arrays in resource_center/utils.rs and PRIORITIZED_KEYBINDINGS act only as a hand-maintained sectioning/ordering overlay (the cheatsheet's triggers are already live-derived; only its sectioning is curated). Choose among: (a) replace everything with one unioned live manifest and delete the arrays, sectioning by BindingGroup; (b) reconcile by build-time codegen; (c) converge the editor's and cheatsheet's independent source walks onto one shared, filter-parameterized walk over the live keymap, keep the curation arrays as CI-guarded data, and defer the fixed+editable union; (d) coexist with only a resolvability test; or (e) defer and declare the settings catalog canonical.

**Stakes.** The North Star is 'what the UI shows is the truth.' The brief's framing — three drifting sources that cannot all be right — is half true: trigger data already has one source (the keymap), the cheatsheet's triggers are already live-derived, and the cheatsheet's Fundamentals catch-all guarantees no live binding is orphaned. The only hand-maintained, drift-prone artifact is the curation overlay (which name goes in which section); a curated name that no longer resolves silently disappears with no test to catch it. So the genuinely contestable design question is narrower than implied: (a) whether to converge the editor's and cheatsheet's independent source walks so they provably read the same keymap, and (b) whether to add the missing resolvability test. The maximal 'delete the arrays and unify fixed+editable into one complete manifest' move is real but gated on fixed-binding identity (A5-Q3/Q4, ~167 user-reachable sites) and would REGRESS the cheatsheet if attempted editable-only — so it is not a Phase-1 prerequisite. Getting this wrong additively (bolt on a fourth catalog) re-creates the discoverability gap; over-scoping it (force the union now) blocks Phase 1 on a large separate refactor for a benefit that is partly a category error, since the editor and cheatsheet legitimately show different filtered sets for different jobs.

_Constrained by:_
- The cheatsheet's TRIGGER data is already live-derived (build_bindings walks get_key_bindings then filters trigger.is_some() && non-empty description); only its SECTIONING is hand-curated via name-membership in the static arrays. So there is no independent third source of trigger data — only a curation overlay over the live list. The arrays' own header says they 'should always align with documentation' (drift policed by hand). — `app/src/resource_center/keybindings_page.rs:136-154,229-253; app/src/resource_center/utils.rs:1-2,8-114`
- The cheatsheet's Fundamentals section is a CATCH-ALL: every binding not in any other static array is chained into Fundamentals, so NO live binding passing the trigger+description filter is orphaned. The only invisibility is the build_bindings filter (triggerless / empty-description), not section membership — so 'live bindings in no section' is structurally zero and does not discriminate between the options. — `app/src/resource_center/keybindings_page.rs:255-277`
- BindingGroup cannot serve as a complete sectioning dimension: lens.group is Option<&'static str> with many editable bindings None, and ALL FixedBinding constructors set group:None. 'Derive sections from BindingGroup' therefore dumps fixed bindings and None-group editables into a catch-all, so a name-keyed sectioning overlay must survive — 'delete the arrays' is illusory. — `A5-Q2 (bindings.rs:797-810; group Option at keymap.rs:316); A5-Q3 (FixedBinding constructors all set group:None, keymap.rs:511-593)`
- The editor and cheatsheet are two FILTERED VIEWS of one keymap, not two independent sources: settings builds from editable_bindings() via from_editable_lens (never returns None, so includes unbound editables); cheatsheet builds from get_key_bindings() via from_lens (returns None for description-less bindings) then filters trigger.is_some(). A single manifest would still feed both with different filters, so Replace does not eliminate the set-difference. — `app/src/settings_view/keybindings.rs:748-784; app/src/resource_center/keybindings_page.rs:136-154; app/src/util/bindings.rs:749-771`
- An editable-only v1 manifest would regress the cheatsheet by at most the ~65 description-bearing fixed bindings (44 custom + 21 empty constructors) that currently survive from_lens; the other ~404 fixed bindings (new/standard/new_per_platform) are description-less and already dropped today. This bounds the cheatsheet-regression risk of any source switch and is why the cheatsheet must stay on get_key_bindings until A5-Q3/Q4. — `A5-Q3 (keymap.rs:511-593,633; from_lens bindings.rs:749-758)`
- The resolvability test is low-risk and uniquely correct: an existing test (App::test + ctx.editable_bindings().find(name)) already spot-checks curated names, so asserting every array name resolves is a direct generalization; unlike build-time codegen it runs against the true cfg/platform-gated registered set. No completeness/conflict/resolvability test exists today across 147+120=267 register sites in 111 files. — `A5-Q13 (bindings_tests.rs:76-116; register sites 147 fixed + 120 editable across 111 files)`
- The only durable catalog key is the editable binding name (already the keybindings.yaml key); fixed bindings are nameless (FixedBinding::as_lens sets name = Default::default()), so a name-keyed manifest is editable-only until A5-Q3/Q4 assign fixed bindings a stable name. — `A5-Q12 (keymap.rs:294; keyboard.rs:155-187); A5-Q3 (keymap.rs:633)`

**Options:**

- **Replace — one live manifest is the only source; delete static arrays, section by BindingGroup** _(high effort · costly)_ — catalog-v1 is a single live walk keyed on name; the cheatsheet becomes a view over the same manifest with sections derived from BindingGroup; the hand-maintained name arrays are deleted; editorial prioritization survives only as a thin overlay; full fixed-binding coverage is phased in once A5-Q3/Q4 give fixed bindings a stable name.
  - 👍 The only option that forces the full fixed+editable union and an honest single complete catalog, and keeps the team committed to finishing the union rather than letting 'defer' become 'never.' Much machinery already exists (the live walk, the durable name key, a semantic group field).
  - 👎 Its two defining moves are not viable as stated. (1) BindingGroup cannot section fixed bindings (all group:None, A5-Q3) or the many None-group editables, so 'section by BindingGroup' silently dumps most bindings into a catch-all and a name-keyed sectioning overlay must survive anyway — 'delete the arrays' is illusory. (2) The full union is gated on A5-Q3/Q4 (~167 user-reachable fixed-binding sites, X5), and until it lands an editable-only 'replace' would REGRESS the cheatsheet by dropping the ≤65 description-bearing fixed bindings it shows today. The 'removes the structural contradiction' premise is partly a category error: the editor and cheatsheet filter the same keymap differently because they have different jobs, and a single manifest still feeds differently-filtered views. Highest coordination cost across product/engine/docs.
- **Reconcile by codegen — generate the static lists from the manifest at build time** _(high effort · costly)_ — keep curation in source as annotations but emit/assert the section and Essentials arrays from a build-time walk of the binding registry, so a static list can never reference a name that does not resolve; runtime keeps the two renderers fed by a generated artifact.
  - 👍 Preserves human curation and both renderers while making name-membership drift impossible by construction, with no runtime engine change.
  - 👎 Bindings are registered imperatively at 267 sites across 111 files, many behind cfg/platform gates, so a build-time generator cannot see the true runtime set without effectively running app init — the snapshot can itself diverge. It is strictly dominated by a RUNTIME resolvability test (App::test, as bindings_tests.rs already does), which sees the real gated set. Adds build-pipeline complexity, still leaves two renderers and two filter policies, and does nothing about nameless fixed bindings.
- **Coexist + resolvability guard — keep all surfaces, add the missing CI test** _(low effort · easy)_ — leave the settings catalog, cheatsheet, and static arrays as-is, but add the resolvability test that does not exist today: assert every static curated name resolves to a live binding.
  - 👍 The cheapest credible step and the correct first increment. The test is a direct generalization of an existing test (App::test + editable_bindings().find(name), bindings_tests.rs:76-116), so it is low risk/effort, and it kills the ONLY real silent-drift vector — a dangling curated name — because the cheatsheet's Fundamentals catch-all already guarantees no live binding is orphaned. Ships this release; preserves all curation and UX; buys time for A5-Q3/Q4.
  - 👎 Stops short of converging the source: the editor and cheatsheet keep walking the keymap independently (editable_bindings vs get_key_bindings), so they can still diverge in which collection/filter they apply even though neither is 'wrong.' Cheatsheet still hides unbound actions and settings still hides fixed bindings — but note that gap is largely by-design and the fixed-clobber risk is A5-Q6's job, not this decision's.
- **Converge the source builder + keep curation as CI-guarded data (defer fixed+editable union to A5-Q3/Q4)** _(med effort · easy)_ ✅ **recommended** — Ship the resolvability CI test (the Coexist increment) as the non-negotiable first step. Refactor the settings editor and the cheatsheet to draw their CommandBinding list from ONE shared source walk over the live keymap, parameterized by an explicit filter policy (editor: editable incl. unbound; cheatsheet: triggered), so the two surfaces provably read the same underlying set. KEEP the static name arrays + PRIORITIZED as a name-keyed curation/ordering overlay, now CI-guarded so names cannot dangle, rather than deleting them. Leave the cheatsheet's source on get_key_bindings so it keeps its described fixed bindings. Defer the full fixed+editable union and any BindingGroup re-sectioning until A5-Q3/Q4 give fixed bindings a stable name/group.
  - 👍 Delivers the achievable part of the North Star NOW — one source walk, curation that cannot dangle — at low/medium cost and easy reversibility, without blocking on the 167-site fixed-binding project or the unsolved scope primitive. It formalizes what the grounding shows is already reality (the arrays are a curation overlay over a live list) instead of pretending to introduce a green-field manifest. It sidesteps the BindingGroup-sectioning trap (group:None for fixed and many editables) and avoids the cheatsheet regression. The shared builder is exactly where the future union plugs in, so it keeps the maximal option open without paying for it prematurely.
  - 👎 Does not produce a single complete surface: the cheatsheet still won't list unbound actions and settings still won't list fixed bindings, so a user expecting ONE place to see everything is under-served until the deferred union lands. The shared-builder refactor is real work touching both build paths and must preserve the editor's ConflictMap/dedup behavior (keybindings.rs:782). It converges/manages the filter divergence rather than eliminating it — though that divergence is largely appropriate to the two surfaces' jobs.
- **Defer — declare the settings catalog canonical, leave cheatsheet and arrays untouched** _(low effort · easy)_ — name the live settings catalog the source of truth for rebinding and conflicts, leave the cheatsheet and its static arrays as a separate quick reference, and do nothing to reconcile them this cycle.
  - 👍 Zero new work; the settings catalog is already live and is where editing happens, so other A5 workstreams proceed without blocking on catalog unification.
  - 👎 Ships the exact additive anti-pattern this question names: two 'live' catalogs both claim authority while the static arrays keep rotting with no guard (a dangling curated name silently vanishes). Cheapest in the short term, most expensive in accumulated silent drift.

### A5-Q10 — HARDENED · _cross-team_ · owner: Cross-team. The keybindings product owner OWNS the in/out-of-scope declaration and the caveat-scoping copy (and must decide whether the catalog is ever an off-machine/published artifact — the pivot for residual risk). The warpui_core keymap engine lead co-owns feasibility (confirms the inactive side is unbuildable today, A6-Q6) and whether/when R5 is built. Product decides scope and the caveat surface; engine confirms sequencing. No new owner needed.

**Decision.** Whether Phase-1 conflict detection and the action catalog claim cross-platform (mac vs linux/windows) truthfulness or explicitly scope to the running OS — and, if scoped, the minimum honesty surface required. Corrected framing: the data model can only conflict-check the running OS today (A6-Q6), and the editable bindings that feed the conflict map are stored locally per machine as OS-resolved strings (not cross-OS synced), so the in-app conflict UI is already truthful for the machine it shows. The real decision is therefore narrow: (a) MUST the design doc explicitly declare cross-platform binding-editing/conflict-checking as out of scope for Phase 1 (vs implying authority it lacks), and (b) does Phase 1 add any runtime caveat, and if so where — a blanket 'this is macOS only' banner, or a caveat scoped to the genuinely cross-OS surfaces (the cloud-synced QuakeMode/ActivationHotkey hotkeys; device-sync). The heavyweight cross-platform feature (Option D / R5) is out of Phase 1 regardless.

**Stakes.** The axis North Star is 'what the UI shows is the truth.' Corrected: single-OS scope does NOT inherently violate it — the settings view only ever displays the running OS's bindings (A6-Q6) and only claims conflicts for that OS, both of which are true, and the editable bindings feeding the ConflictMap live in a local keybindings.yaml as OS-resolved strings (keyboard.rs:95-96,167-187), not synced cross-OS, so a rebind on one machine cannot silently mis-resolve on another through this path. The residual exposure is a lie of OMISSION: the UI never warns that the catalog/conflict result is one-platform, so (i) a user re-applying a binding on a second OS gets no advance warning (but that second machine flags the real conflict when they do), and (ii) if the catalog is ever EXPORTED off-machine as a 'portable' reference (docs, or the R9 change-keybinding agent manifest), the single-OS artifact would be presented as canonical cross-platform — that is the one place the omission becomes a genuine false claim. So the stakes are: avoid OVERCLAIMING cross-platform truthfulness in the design doc and in any off-machine catalog artifact. The cost of getting this wrong is a credibility hit on the axis ('truthful conflicts' that aren't, off-machine), not a live in-app falsehood for the typical single-machine user.

Treats the keybindings settings page as the developer tool its audience largely is.
  - 👎 Injects ~hundreds of machine strings (code_editor:find, ai_block:rich_content_secret_first_char_position) into a list users scan by human description — visual clutter and a leaky-abstraction feel. Names were never designed as display strings; some are unflattering implementation detail. Couples the UI to an internal naming convention, making future renames user-visible/breaking. The 9 same-name/different-description rows show identical badges, which reads as a bug rather than intended linked-binding behavior. Fixed bindings have empty names (keymap.rs:633) so badges would be blank for them until A5-Q3/Q4.
- **Humanized alias index** _(high effort · costly)_ — Don't surface raw ids; build a curated/synthesized human-friendly synonym set (or Title-Case-from-name labels) and index those for search, keeping descriptions as the only visible text.
  - 👍 Best pure-UX outcome: users search in natural language, never see namespace:action, and matches feel intuitive — the cleanest possible discoverability without exposing internals.
  - 👎 No alias data source exists — name is the sole id and description already serves as the human label, so this is net-new content to author and maintain across the registration surface the answers doc sizes at 93 files / 146 register calls / 456 constructor sites (the brief's '109 files' is not the verified figure), with drift risk. It also fails the stated need: the R9 agent and keybindings.yaml require the REAL name (A5-Q12, A1), so an alias index that hides the canonical token leaves power users unable to discover what to type. High effort for a benefit description already mostly provides.
- **Defer name-search entirely (description+keystroke only)** _(low effort · easy)_ — Ship v1 with search unchanged (description + keystroke only); do not index OR display names at all.
  - 👍 Zero code change and zero clutter; descriptions already cover most natural-language queries, and the conflict/catalog work lands without touching the search path. Lets the team defer the fixed-binding-id (A5-Q3/Q4) and scope (A5-Q8) questions that complicate truthful name-search.
  - 👎 Foregoes the axis headline AND the agent-discoverability value. Users who know the id (from yaml or agent output) can't find the row by it; the gap between what the agent speaks (names) and what the UI lets you search (descriptions) persists. Also leaves the currently-unsearchable unbound/empty-description editables (answers :1985) unfindable. Cheap now, but re-opens the same decision later with no learning gained. Strictly dominated by Index-only, which costs the same one-function edit but delivers the headline.

**→ Recommendation: Hidden search key + reveal-on-detail.** Decompose the decision: indexing binding.name is the non-negotiable Phase-1 FLOOR — a single fuzzy-score line in filter_bindings_including_keystroke (bindings.rs:633-687) that delivers the literal axis headline and rescues the currently-unsearchable unbound/empty-description editables (answers :1985); every non-defer option includes it. The contested half is DISPLAY, and reveal-on-detail wins because (a) it is the only low-cost option that satisfies the DISCOVERY need — learning a canonical token from a description-found row — which index-only structurally cannot; (b) the host already exists (render_clicked, keybindings.rs:307-366), so the marginal cost over index-only is a copyable token in an existing region, not a new panel; (c) the two real consumers (name-keyed R9 manifest A5-Q12, name-keyed keybindings.yaml A1) need the id copyable, not prominent. The always-visible badge pays an ongoing clutter and abstraction-coupling cost for a benefit only power users need occasionally, and its same-name/different-description duplicate-badge artifact reads as a bug. The alias option invents a maintenance burden across ~456 constructor sites with no data source and still hides the canonical token the agent requires. Defer/defer-name-search bank no learning and are dominated by Index-only. The safety worry is answered: search runs over the post-dedup list (keybindings.rs:538-539,782) so it provably cannot resurface dedup-hidden twins. Two honest caveats now corrected: the 'highlight the matched token' mitigation is NOT implementable in the collapsed list (highlight indices are over the description, bindings.rs:650-651) — the token only appears on expansion; and name-search covers editable bindings only until A5-Q3/Q4 give fixed bindings a stable id. If design review on the token stalls, fall back to the added 'Index-only' option to keep Phase 1 unblocked, then promote to reveal/badge per telemetry — reversibility is easy in both directions.

- _Residual risk:_ The recommendation commits to building the reveal-on-detail token BEFORE running the very power-user/R9 interview that what_would_settle_it prescribes ('do you need to see/copy the canonical id, or only search by it?').
