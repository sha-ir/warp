# Improved Keybindings — Decision Briefs (adversarial)

**Date:** 2026-06-13
**Status:** Decision briefs for the 38 non-code (`user-product-decision` + `cross-team-decision`) design-readiness questions
**Companion to:** [`...design-readiness-questions.md`](../2026-06-13-improved-keybindings-design-readiness-questions/README.md) (the questions) and [`...code-investigation-answers.md`](../2026-06-13-improved-keybindings-code-investigation-answers/README.md) (the verified facts these briefs are grounded in)

## Method

Each decision got a brief (named options, each with a steelman and an adversarial *what-breaks*, plus effort/reversibility), grounded in the verified code facts. Each brief was then **red-teamed** by an independent agent that re-checked the grounding, hunted for a missing option, priced the effort/dependencies honestly, and either upheld, hardened, **flipped**, or downgraded-to-toss-up the recommendation. A final pass sequenced all decisions into waves and surfaced the linchpins.

Verdicts: **33** HARDENED · **5** FLIPPED

> These are **recommendations to decide against**, not decisions. Each names its owner and what would settle it. Read the sequencing section first.

## Decision sequencing

Treat A1-Q1 as the gate to everything: rule NOW that R3b (the context/platform record schema) is deferred to Phase 2, which resolves the end-goals-vs-report contradiction and collapses the whole schema-dependent question chain out of Phase 1. In the same Wave-0 sitting, lock the cross-cutting contracts that have ~0 code but contaminate everything downstream - X2 (harden the loader, stay flat now, migrate to records once in Phase 2 behind a duplex deserializer + absent-vs-parse-error split), X3/A1-Q11 (import/export is same-platform-only, flat reuse, no encoding commitment), X11 then X4 (ratify the canonical-name authority before freezing the versioned catalog key), X8 (decoupled reset-all-reapply watcher, route file-format forward-compat to X2, reject any Phase-1 user-layer object), and X10/A5-Q10 (the conflict honesty floor and current-OS-only doc declaration). Then build Phase 1 over the flat map (Wave 1): the flagged hot-reload watcher + ledger trait, the hardened write path, the warn banner, search index, and the honest-floor conflict relabel - and crucially TAKE X13's resolution-snapshot capture before any of Phase 2 reorders bindings(), because that dump is irreversible. Phase 2 then splits into a foundations wave (A2-Q2/A2-Q3/A2-Q5 schema-and-mechanism, A3-Q2/A3-Q5/A3-Q13 layer+unbind engine which ships first to unblock R3b's inject path, plus X13's harness gate) and a consumers wave (grammar/serializer, scoped settings UI, conflict truthfulness tiers, and the platform read-only editor). Phase 3 modal editing (A4-Q1/Q2/Q3) comes strictly last and is where X11's alias registry is finally built and seeded at the first deliberate rename. The two live decisions a lead must force before writing Phase-1 code are: publish the A1-Q1 defer ruling so X11/X2/X8 read consistently, and pick ONE Phase-1 portability story - same-OS-only (X3/A1-Q11) versus a cmd<->ctrl read-rule slice (A6-Q10) - because those two cannot both be the promise."

### Linchpin decisions (resolve these first)

- **A1-Q1** — The single highest-fan-out ruling. Deciding to DEFER R3b (rich context/platform schema) to Phase 2 resolves the documented end-goals-vs-report contradiction and nullifies the entire schema-dependent question chain for Phase 1 (round-trip, cross-platform import, unknown-name migration, schema back-compat). It directly gates A1-Q2, A1-Q10, A1-Q11, A1-Q15, frames X2/X11/A6-Q10, and determines whether Axis 1 is a one-week quick win or a multi-week schema project. Until this is settled, no Phase-1 file-writer can be scoped.
- **X2** — The canonical file-schema authority. Its 'harden the loader now, stay flat in Phase 1, migrate to records once in Phase 2 with a duplex/untagged deserializer + absent-vs-parse-error split' is the seam every file-touching decision inherits. Gates X3 (export is just another legacy flat file), X8 (file-format forward-compat is routed here), A1-Q10 (alias write shares the chokepoint), A1-Q11 (origin-platform stamp rides the envelope), A2-Q3 (the record shape it reserves), and A6-Q10 (full {mac,other} pair needs this schema). It is the data-loss firewall the whole installed base depends on.
- **X13** — The regression net the entire Phase-2/3 refactor program is gated on. Its irreversible CAPTURE of the (context,keystroke,OS)->winning-action baseline must land in Phase 1 before the first bindings() reorder (R2); after that the golden cannot be re-derived cleanly. Every axis's 'no cross-axis regression' acceptance claim (Axis 2/3/4/5/6) is gated on this diff existing, and it supplies Axis 6 its target-OS injection seam. It unblocks confidence rather than features, but nearly every engine decision depends on it.
- **A2-Q3** — The Phase-2 persistence linchpin. The record-list [{name,trigger,context?,platform?}] shape co-decides A2-Q4 (override targeting), A2-Q6 (grammar/serializer), A2-Q8 (interning), A2-Q15 (write path) and feeds A2-Q18 (settings UI), A5-Q14 (conflict scope field), the catalog platform column (X4), and A6's platform field. Almost every Phase-2 engine deliverable that persists or reads scope funnels through this single schema choice.
- **A2-Q5** — The mechanism-and-dependency selector that sets Phase-2 scope. Choosing mutate-vs-inject and which use-case class (rebind disjoint-context fork vs add net-new scope/suppress) determines whether Axis 2 can ship standalone or hard-requires the full Axis-3 (layer,recency) precedence store + Unbound. It hard-couples A2-Q3/A2-Q4 and decides whether A3-Q1/A3-Q3/R2 get pulled into Phase 2 - i.e. it shapes the size of the entire engine wave.
- **X11** — The cheap-but-high-fan-out name-authority contract. Naming a canonical-name DRI and ratifying the unknown-name policy must happen BEFORE the R9 catalog v1 (X4) turns action name into a committed public id. It gates X4's stable key, feeds A5 catalog and the agent skill, owns the A1-Q10 alias facet, and is the just-in-time build trigger for Axis-4 Step-D renames. ~0 code to decide, but freezing the wrong key contaminates two consumers and Phase-3 migration.

### Recommended waves

- **Wave 0 - Cross-cutting contracts & scope rulings (settle before ANY code; near-zero code):** A1-Q1, X2, X3, X11, X4, X8, X10, A5-Q10, A6-Q10
  - These are rulings, not builds, and every Phase-1 file-writer/contract is downstream of them. A1-Q1 must first resolve the R3b scope contradiction (defer to Phase 2). X2 then fixes the loader-hardening + flat-now/records-later + duplex-deserializer strategy that all file work inherits, and X3 sets the import/export portability promise (same-platform-only, flat reuse, no encoding commitment). X11 ratifies the canonical-name authority before X4 freezes the versioned catalog manifest and turns action name into a public id. X8 settles that the hot-reload watcher ships decoupled (reset-all reapply, no persistent applied-set) and routes file-format forward-compat to X2 while rejecting any Phase-1 user-layer object. X10 fixes the four-tier conflict-truthfulness contract and the Phase-1 honesty floor, A5-Q10 mandates the doc scope declaration (current-OS-only), and A6-Q10 makes the R5 split call (whether any Phase-1 cmd<->ctrl portability read-rule slice exists vs full pair deferred to Phase 2). Locking these prevents the Phase-1 quick wins from being built forward-incompatible and discarded.
- **Wave 1 - Phase-1 build (quick wins over today's flat HashMap; no engine/schema change):** A1-Q2, A1-Q14, A1-Q15, A1-Q10, A1-Q11, A3-Q14, A3-Q18, A5-Q1, A5-Q11, A5-Q14, A5-Q15, X13
  - All buildable over the flat map once Wave 0 rulings hold. A1-Q2 gates hot-reload behind a dedicated FeatureFlag with a clean disabled path; A3-Q14 ships the applied-names ledger behind a 3-method trait that must honor that flag in lockstep. A1-Q14 (malformed-reload error surface) and A1-Q15 (IndexMap stable ordering + the atomic temp-rename write that fixes the only runtime data-loss bug) harden the write path. A1-Q10 ships the warn-on-unknown-name banner (alias CODE deferred to Step-D), A1-Q11 labels and guards same-platform-only import. On Axis 5, A5-Q1 lands the resolvability CI test + shared source builder, A5-Q11 does the mandatory honest relabel + ConflictMap rekey floor, A5-Q14 ships warn-only-advisory save, A5-Q15 adds the hidden name-search index, and A3-Q18 adds the apply-time prefix-shadow guard riding chord capture (R8). Critically, X13's CAPTURE - the frozen pre-refactor resolution baseline - must be taken during this wave, because all of Phase 1 sits safely before the first bindings() reorder and the dump is irreversible once R2 lands.
- **Wave 2 - Phase-2 foundations (record schema + layer/precedence engine + harness gate):** A2-Q2, A2-Q3, A2-Q5, A2-Q1, A3-Q2, A3-Q5, A3-Q13, X13
  - The engine core. A2-Q2 fixes the context-only engine key with platform as a reserved load-filter field, which co-decides A2-Q3's record-list schema; A2-Q5 then selects the mechanism (mutate-vs-inject) and the use-case class, which sets whether full R2 is pulled in. A2-Q1 does the public-alias vocabulary RFC in parallel (design now, publish incrementally). On Axis 3, A3-Q2 proves the N-layer resolver against a synthetic mode-pack fixture (policy deferred), A3-Q5 ships the additive name-scoped unbind + match_custom leak fix, and A3-Q13 ships the named-editable layer + keystroke-addressable Unbound tombstone - this layer ships FIRST and is the actual unblocker for R3b's inject path. X13's harness+gate is built just-in-time at this R2 boundary so every refactor in this and later waves diffs against the Wave-1 golden. (X13 appears here as build, distinct from its Wave-1 capture.)
- **Wave 3 - Phase-2 consumers (grammar, conflict truthfulness, platform editor, scoped settings UI):** A2-Q6, A2-Q10, A2-Q18, A3-Q19, A6-Q2, A6-Q1, A6-Q11
  - These consume the Wave-2 schema and engine. A2-Q6 ships the Display serializer now (read-only catalog/export) and defers the FromStr parser; A2-Q10 symmetrizes unknown-atom eval so a bad atom degrades to inert-within-scope. A2-Q18 un-collapses same-name rows by registered context and makes existing scoped rows editable in place (serialize-and-match, no parser). On Axis 6, A6-Q2 builds the keymap-only editor with the serde-additive constraint, A6-Q1 shows read-only inactive-platform display with portable current-platform edits, and A6-Q11 reserves R6's target_os parameter at design time while staging the inactive-conflict build. The deeper conflict tiers (X10 v1/v2/v3) and the A5-Q14 gate/swap half also build here once the scope field and platform pair exist.
- **Wave 4 - Phase-3 pluggable modal editing (Axis 4):** A4-Q1, A4-Q2, A4-Q3
  - Strictly after Phase 2: per-mode keymaps are unusable without context-scoped overrides (R3b) and layer precedence (R2). A4-Q1 cuts user-editable per-mode keymaps to post-Phase-2 and ships the engine + Helix proof + dropdown with a forward-compatible Modal:{engine}:{submode} seam confirmed against R3b at Phase-2 exit. A4-Q3 sets the tiered Helix acceptance bar as a Phase-3-entry spike decision, not a commitment made now. This is also where X11's alias registry is finally BUILT and seeded (Step-D is the first deliberate rename) and A1-Q10's alias CODE ships.

### Contradictions / tensions to resolve

- **A1-Q1 ↔ X2 ↔ X8 ↔ X11** — Documented scope contradiction the whole sequence inherits: the end-goals doc (L52-53) lists R3b as an Axis-1/Phase-1 leaf, while the report roadmap (section 7) and dependency spine (L117) place R3b in Phase 2. A1-Q1, X2, and X8 all resolve it in favor of the Phase-2 placement (defer records, harden the flat loader now). X11's brief flags that its own 'build now' wording silently assumed R3b-in-Phase-1; once A1-Q1's defer ruling holds, X11 must be read as build-just-in-time (Step-D). The lead must publish the A1-Q1 ruling FIRST and propagate it, or X11/X2/X8 briefs can be read inconsistently.
- **X3 ↔ A1-Q11 ↔ A6-Q10** — Phase-1 cross-OS portability is contested. X3 (REC=A', literal flat reuse, same-platform-only, warn on cross-OS) and A1-Q11 (same-platform-only v1, guard+label) both decline to pull any of R5 into Phase 1 and make NO cross-OS portability promise. A6-Q10 (read-rule-first) instead wants to ship the A6-Q12 back-compat READ/resolution rule in Phase 1 so the common cmd<->ctrl case ports cross-OS with no new on-disk representation - which X3 explicitly enumerates as its rejected Option B. The lead must pick one Phase-1 portability story: same-OS-only (X3/A1-Q11) OR a cmd<->ctrl read-rule slice (A6-Q10). They cannot both be the Phase-1 promise.
- **A2-Q3 ↔ X2** — Schema-firmness mismatch. X2 commits, as a settled Phase-2 deliverable, that 'records land once in Phase 2' with the {name,trigger,context?,platform?} shape reserved. A2-Q3 keeps that very record list CONDITIONAL on (1) product confirming Phase 2 needs NEW per-context scopes and (2) A2-Q5 favoring inject/recency precedence - otherwise it recommends deferring the schema change further. If A2-Q3's conditions fail, X2's reserved record shape may never materialize (or stay flatter), so X2's 'migrate once' planning must treat the record shape as provisional until A2-Q5/A2-Q3 are jointly decided in Wave 2.
- **A2-Q5 ↔ A3-Q2 ↔ A3-Q13** — Fixed-fork migration timing. A2-Q5's recommended added option D migrates the ~19 flagship Vim Fixed forks to named EditableBindings in Phase 2 (assigning names, pulling a narrow slice of A3-Q1 forward). A3-Q2 explicitly KEEPS A3-Q1 (Fixed migration) and A3-Q3 (stable identity) in Phase 3 and does NOT migrate real vim in Phase 2; A3-Q13 defers context-aware fixed REMAP behind R3b. The tension is whether ANY Fixed-fork migration happens in Phase 2 (A2-Q5 option D) or none (A3-Q2/A3-Q13 keep it in Phase 3). Resolve by confirming whether the disjoint-context vim rebind use-case is in Phase-2 scope; if yes, A3-Q2's 'no real-vim migration in Phase 2' boundary must move.
- **X4 ↔ X11 ↔ A1-Q10** — Resolved-but-load-bearing tension on the stable-name key. X4 freezes the editable-name as the agent's committed public id and binds the agent contract to it; X11 and A1-Q10 acknowledge action names can drift (Step-D renames). X4's own correction notes Step-D is Phase 3, so the key is stable through Phase 1 - but only if the X11 alias registry is consulted at catalog generation once Step-D lands. The contract (X11) must be ratified before X4 ships, or the catalog freezes a key that later renames silently break for the agent.
