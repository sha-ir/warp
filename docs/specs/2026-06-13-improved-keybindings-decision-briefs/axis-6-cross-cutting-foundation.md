## Axis 6 — Cross-cutting foundation (platform-in-data-model)

### A6-Q1 — HARDENED · _product_ · owner: Product owner for the keybindings/settings initiative (the PM who owns R5), with co-sign from the warpui/settings engineering lead — because the edit-vs-display line directly sets whether the Axis-2 record schema, a release-path validator, and a platform-parameterized conflict engine become hard prerequisites, and because the engineering lead must confirm the cheaper boundary (faithful inactive display from retained-registration data + portable write path WITHOUT those three) is real. The investigation doc classifies A6-Q1 as user-product-decision; note the 'rule out B for Phase 1' half is largely engineering-cost-driven, while the display-vs-portable-edit-vs-defer half is the product/demand call.

**Decision.** For R5's "show/edit both mac and linux/windows bindings" end state, decide the editability boundary for the INACTIVE (non-running) platform's binding. The load-bearing, must-decide-before-schema call is binary: is full INDEPENDENT editing of the inactive platform in Phase-1 scope (which forces the Axis-2 record schema, a release/edit-path platform-parameterized validator, and a platform-parameterized conflict engine) or NOT? Given that answer is "not yet," a second, smaller, reversible call follows: how does the cross-platform surface treat the inactive side and what does a current-platform edit PERSIST — read-only display of defaults with edits persisted resolved (status quo write path, inactive column is decorative); read-only display PLUS edits persisted in unresolved/portable form so a customization resolves correctly on the other OS and the inactive display stays truthful; or no cross-platform surface at all this phase (engine-only).

**Stakes.** This boundary is the single biggest scope multiplier in Axis 6, but the truly blocking decision is narrower than the brief implied. Full independent inactive editing silently pulls in (a) the Axis-2 record-based file schema (the flat one-string-per-name file physically cannot hold a {mac:'cmd-[', other:'ctrl-shift-{'} pair — keyboard.rs:169,174), (b) a net-new release/edit-path platform-parameterized validator (today's edit path validates nothing; the only validator is debug-only, one-directional — keybindings.rs:669-699, bindings.rs:918-933), and (c) a target-OS-parameterized conflict engine (ConflictMap is keyed on the current-OS-resolved keystroke — keybindings.rs:104-133) — and it asks a user to edit, match, and conflict-check a binding their compile-time-locked build can never run or test (OperatingSystem::get is cfg-fixed, no native setter — platform/mod.rs:669-683). RULING THAT OUT for Phase 1 is what keeps the schema flat and Axis 6 parallel; both display variants and full-defer satisfy that. The remaining display-vs-portable-edit-vs-defer choice is reversible and cheap, but it has hidden teeth: a faithful inactive display of the genuine-divergence MAJORITY (~66% of sites — A6-Q5) is only possible if A6-Q3 commits to the {mac,other} pair representation; if A6-Q3 picks the cmd_or_ctrl bool instead, the inactive column cannot be rendered truthfully and the whole display value collapses. The doc rightly flags that "show both" was conflated with "edit both"; the sharper correction is that "edit both" was further conflated with "edit the inactive side independently" — most multi-OS users actually want "my one config works on both machines," which is a portability/persistence property, not an inactive-platform editor.

_Constrained by:_
- OperatingSystem::get() is compile-time-fixed per native build (cfg_if over target_os/family) with NO parameter and NO runtime setter; the only non-compile-time path is a wasm OnceLock set once from the browser user agent. A single native build literally cannot resolve, match, run, or test the inactive platform's binding, so EDITING a platform you cannot exercise is inherently riskier and locally unverifiable, while DISPLAY carries no such hazard. — `crates/warpui_core/src/platform/mod.rs:669-683; wasm.rs:8 (A6-Q15 answers:2447)`
- Keystroke has fields ctrl/alt/shift/cmd/meta/key and NO cmdorctrl/platform field; the cmdorctrl token is resolved to cmd (mac) or ctrl (else) at PARSE time. So a binding's cmd-vs-ctrl identity is OS-baked before display or persistence; a faithful cross-platform surface needs the unresolved binding plus a target-OS resolver, not glyph rendering alone. — `keymap.rs:320-328, 914-919 (verified directly)`
- cmdorctrl is the ONLY pure cmd<->ctrl swap (~139 sites) and is resolved away at parse time. The MAJORITY of divergence is genuine key/chord difference (cmd_or_ctrl_shift ~140 CORRECTED from 181; with_mac/with_linux 157; new_per_platform 13) and the inactive side is never constructed or stored because the builders no-op on the OS they don't match. 'Show both' cannot be synthesized by a cmd<->ctrl rule for most bindings; both sides must be carried through registration. — `A6-Q5 answers:2156 (keymap.rs:688-713, 914-919)`
- The persisted file is HashMap<String, PersistedTrigger(String)> (one slot per name) and the ONLY write path maps via Keystroke::normalized(), which emits resolved ctrl-/cmd- with no cmdorctrl branch. Therefore: (a) a full {mac,other} pair cannot be persisted without Axis-2's record schema; (b) a cmdorctrl token can be READ from disk but cannot be WRITTEN/round-tripped today; (c) crucially, a user's current-platform edit is persisted in RESOLVED form, so it is not config-portable and does not survive being carried to the other OS — the brief's Option A is silent on this. — `keyboard.rs:169,174,176-180; normalized() keymap.rs:970-993 (A6-Q9 answers:2311,2315)`
- The settings edit path runs NO validator: confirm_keystroke_editing unconditionally calls set_custom_keybinding with no has_conflict gate; ConflictMap is HashMap<Keystroke,usize> keyed on the CURRENT-OS-resolved keystroke and does same-platform duplicate detection only; is_binding_cross_platform is debug-only, registration-time, one-directional (returns Yes on mac, only flags a stray cmd on non-mac). Editing the inactive platform safely requires a brand-new release/edit-path, platform-parameterized validator AND a target-OS-parameterized conflict map that do not exist today. — `keybindings.rs:104-133,669-699; util/bindings.rs:918-933 (answers:1836; A6-Q13:2393,2409)`
- displayed() has no target-OS parameter, branches on OperatingSystem::get().is_mac() five times, and is called across 21 files / 41 sites (all current-OS hint surfaces). A read-only displayed_for(target_os) is additive and confined to ~3 settings-adjacent callers; threading a target-OS param through displayed() would be 21-file mechanical churn. This bounds the display path as cheap relative to the edit path. — `keymap.rs:998-1065 (A6-Q15 answers:2451-2462)`
- HIDDEN DEPENDENCY: a faithful inactive-platform display of the genuine-divergence majority is only possible if A6-Q3 commits to a {mac,other} pair representation carried through registration; option (a) cmd_or_ctrl: bool on the flat Keystroke struct cannot express key-level divergence (cmd-[ vs ctrl-shift-{), so under (a) the inactive column degrades to lossy cmd<->ctrl synthesis — the very truthfulness regression the brief warns against. The recommendation silently assumes A6-Q3 = (b). — `A6-Q3 design-doc:901-906; A6-Q5 answers:2154; A6-Q6 answers:2180`

**Options:**

- **Read-only display of inactive platform (edits persist resolved, status quo write path)** _(med effort · easy)_ — The settings/catalog surface faithfully shows the inactive platform's DEFAULT binding via an additive displayed_for(target_os) over retained-at-registration {mac,other} data; only the current-platform binding is editable, and that edit persists as today (resolved current-OS string).
  - 👍 Strictly inside what one native build can honestly assert, and the cheapest way to land the 'here is what your shortcut does on the other OS' value. Avoids all four edit blast-radius items (Axis-2 record schema, edit-path validator, target-OS conflict map, target-OS test seam). Ships in Phase 1 in parallel with the engine. displayed_for(os) is ~3 callers.
  - 👎 Decorative, not portable: because the edit path persists RESOLVED strings (keyboard.rs:180), a user who rebinds on Mac gets NO change to their Linux column and their customization does NOT follow a carried/synced config — so for CUSTOMIZED bindings the value is only 'see the default of the other OS,' the weakest slice of R5. Faithfulness of the inactive column depends on A6-Q3 landing the {mac,other} pair; under cmd_or_ctrl bool it degrades to lossy synthesis. Customized rows must label the inactive value as the platform DEFAULT, not the user's choice.
- **Read-only inactive display with portable current-platform edits (RECOMMENDED)** _(med effort · easy)_ ✅ **recommended** — Same read-only inactive display, PLUS the current-platform edit persists in unresolved/portable form (cmdorctrl token where symmetric) so the customization resolves correctly on the other OS when the config is carried/shared, and the inactive display reflects that resolution rather than a stale default. The inactive side is still never independently editable.
  - 👍 Delivers the actual North-Star value most multi-OS users want — 'my one config works on both machines' — which is a persistence/portability property, not an inactive editor, so it sidesteps the entire edit blast radius (no per-platform pair to persist for the symmetric class, no target-OS conflict engine, no edit-a-binding-you-cannot-run hazard). For the symmetric cmdorctrl class a single portable edit effectively rebinds both OSes; for the genuine-divergence class it cleanly degrades to display-only. Incremental cost over plain Option A is just the unresolved write-path that A6-Q9 already flags the engine needs anyway, plus the A6-Q12 read rule the portability promise needs regardless. Still a strict subset of full edit, forecloses nothing.
  - 👎 Adds two dependencies over plain display: the unresolved write-path change (A6-Q9: cmdorctrl can be read but not round-trip-written today) and the A6-Q12 back-compat read rule (so an existing resolved 'cmd-d' is not misread as a deliberate mac-only override). If the Phase-1 engine ships portability only for DEFAULTS and not for the user-edit write path, this collapses back to plain Option A. It does NOT let a power user set DIFFERENT bindings per OS (the asymmetric case) — that still needs full edit. Faithful inactive display still depends on A6-Q3 = {mac,other} pair.
- **Full independent editing of inactive platform** _(very-high effort · one-way)_ — The user can edit, conflict-check, and persist the Linux binding while running on Mac (and vice versa), as a true symmetric per-platform editor with asymmetric overrides.
  - 👍 Matches the literal 'edit both' phrasing and is the ONLY option that satisfies asymmetric demand — a power user who wants cmd-K on Mac but alt-K on Linux for ergonomic reasons. Most complete realization of platform-in-the-data-model; avoids a future second feature if that demand turns out to dominate.
  - 👎 Pulls in the whole downstream spine: persisting an inactive edit needs the Axis-2 record schema (flat one-slot-per-name file cannot hold a pair); a net-new release/edit-path platform-parameterized validator (today's edit path validates nothing, is_binding_cross_platform is debug-only/one-directional); a target-OS-parameterized conflict engine (ConflictMap is current-OS-resolved); and a target-OS test-injection seam or CI cannot assert the other platform resolves/conflicts/validates. The user edits a binding the build can never run or test (OperatingSystem::get is compile-time-fixed) with no obvious capture UX for a mac chord on Linux hardware. Migration-bearing schema/serde change. High regression risk; serializes Axis 6 behind Phase 2.
- **Defer the cross-platform surface entirely (engine-only this phase)** _(low effort · easy)_ — Ship the portability/unresolved-model engine (so a binding is correct on whatever OS it runs on and a carried config resolves sanely) but expose NO inactive-platform display or edit yet; the settings UI stays current-OS only.
  - 👍 Most of R5's real value (a config that is automatically right on both OSes via the cmdorctrl/unresolved model) is delivered WITHOUT any cross-platform editor. Fully de-risks Phase 1, lets the Axis-2 record schema settle before any cross-platform surface is committed, validates demand before investing, and — by the brief's own 'display is additive/reversible' logic — forecloses nothing because display can be layered later. The honest fallback if the display-feasibility spike fails or demand data is absent.
  - 👎 Leaves R5's visible 'show both' promise unfulfilled; the discoverability/truthfulness win (a Mac user seeing what a Linux teammate gets) is absent. Defers the display-vs-edit learning to later with the same uncertainty. Still requires the separate A6-Q3 unresolved-representation decision to land for portability — it removes only the UI surface, not the model work.

**→ Recommendation: Read-only inactive display with portable current-platform edits (RECOMMENDED).** The decision that MUST be made now is to rule out full INDEPENDENT inactive-platform editing for Phase 1 (Option B): only B forces the Axis-2 record schema, a release/edit-path validator, and a target-OS conflict engine as hard prerequisites, and only B asks a user to edit a binding their compile-time-locked build can never run, match, or test (platform/mod.rs:669-683). Ruling B out keeps the file schema flat, keeps Axis 6 parallel with Phase 1, and is robustly supported by code. Among the remaining read-only options, the portable-edit variant beats plain display because the brief's Option A is silent on a load-bearing fact a skeptical reviewer will immediately probe: with today's write path the user's edit persists RESOLVED (keyboard.rs:180), so it is not config-portable and the inactive column is mere decoration — whereas the actual value multi-OS users want ('my one config works on both machines') is a portability/persistence property the engine already needs (A6-Q9 flags the cmdorctrl write-path change; A6-Q12 flags the read rule). Portable-edit delivers that for the symmetric class and degrades cleanly to display for the genuine-divergence majority, all without the edit blast radius. It beats full-defer (Option D) because the incremental cost over the shared engine is small and it realizes R5's visible 'show both' promise; it beats full-edit (Option B) because B's very-high, migration-bearing cost should be paid only after demand for inactive editing — specifically ASYMMETRIC per-OS overrides — is demonstrated, not assumed from the word 'edit.' Two honest caveats make this signable rather than optimistic: (1) the recommendation is conditional on A6-Q3 committing to the {mac,other} pair representation — under the cmd_or_ctrl-bool alternative, faithful display of the ~66% genuine-divergence majority is impossible and the recommendation must fall back to Option D; (2) if the Phase-1 engine does not extend portability to the user-edit write path, portable-edit collapses to plain Option A and full-defer becomes the cleaner choice. Because the display-vs-portable-edit-vs-defer refinement is itself cheap and reversible, it can be finalized on a demand signal without blocking the start of Phase-1 engine work.

- _Residual risk:_ The strongest surviving counter-argument: the genuine-divergence majority (~66% of sites — A6-Q5) is precisely the population a power user might want to customize DIFFERENTLY per OS (e.g. cmd-K on Mac, alt-K on Linux for ergonomics). Neither read-only display NOR portable-edit can satisfy that asymmetric demand — only full independent editing (Option B) can. So if the product demand data comes back showing the wanted capability is asymmetric per-platform overrides rather than 'trust portability and see the resolution,' the recommendation's cost-deferral was wrong and B's Axis-2-schema + validator + conflict-engine cost must be paid after all, having lost the time spent on the display surface. Secondary residual: the whole read-only family's truthfulness is hostage to A6-Q3 landing the {mac,other} pair; if A6-Q3 picks the cmd_or_ctrl bool, the inactive column degrades to lossy cmd<->ctrl synthesis (wrong for meta/super and for cmd-[ vs ctrl-shift-{), turning the headline feature into a confident-but-wrong glyph — at which point Option D (engine-only, no surface) is the safer ship.

### A6-Q2 — HARDENED · _product_ · owner: Keybindings/Settings product lead (user-product-decision per A6-Q2), with the warpui_core/settings engineering lead as REQUIRED co-signer on the serialization constraint — A6-Q4 makes the Keystroke struct a cloud-synced + UserDefaults-persisted format, so the serde-additive guard (#[serde(default)] vs Trigger-level pair vs versioned migration) is an eng-scoped gate. Additionally name a DRI for the separate global-hotkey resolution bug (cmd->ctrl vs cmd->Super policy + optional per-platform override) so the decoupled item does not go unowned.

**Decision.** Fix the scope boundary of R5 'platform in the data model' / the cross-platform editor: whether it covers only the keymap (keybindings.yaml), or also the global-hotkey/QuakeMode and slash-command keystrokes that persist as Option<Keystroke> in cloud-synced settings.toml. Re-scoped after attack into two separable sub-decisions: (1) the DATA-MODEL serde constraint (non-deferrable, owned by A6-Q3), and (2) the EDITOR/feature scope for the global hotkey (deferrable; the global-hotkey cross-platform divergence is a settings-resolution decision, not a keymap-editor display feature).

**Stakes.** Keystroke is a shared type and the two global-hotkey settings are the only cloud-synced keystroke consumers. The genuinely non-deferrable risk is the silent-reset hazard: the Keystroke STRUCT serde form is a live persisted format with NO #[serde(default)] — the platform-native store (UserDefaults/registry) ALWAYS serializes struct-form (and cloud does too when FeatureFlag::SettingsFile is off), so if the A6-Q3 representation adds a non-defaulted field to the struct, users' synced/locally-persisted global hotkeys silently reset to default. That hazard is owned by A6-Q3 and must be gated regardless of product scope. The product stakes are NARROWER than the brief implied: the synced mac cmd-` global hotkey is NOT unmatchable on Linux — global_hotkey.rs:105-107 registers cmd as SUPER and displayed() renders it as Logo, so its display already matches its behavior. The real divergence is (a) cmd->Super differs from the keymap's cmd->ctrl (cmdorctrl) convention, and (b) Super-combos are frequently intercepted by the Linux/Windows WM — both settings-resolution concerns. So choosing scope wrong risks either (a) over-investing Phase-1 keybindings-editor effort in a cosmetic global-hotkey display that closes no truthfulness gap, or (b) widening R5 into a settings per-platform schema + cloud-sync migration that can reset users' synced hotkeys. This must be fixed before schema/UI work because it sets the blast radius and the dependency spine.

_Constrained by:_
- Keystrokes persist in TWO surfaces: keybindings.yaml stores PersistedTrigger(String) via Keystroke::normalized() (a local file, HashMap<String,PersistedTrigger>, with no SyncToCloud registration), while global-hotkey keystrokes persist as Option<Keystroke> — QuakeModeSettings.keybinding and ActivationHotkeyKeybinding. — `app/src/settings/mod.rs:334-338; app/src/terminal/keys_settings.rs:13-50; app/src/keyboard.rs:33,169`
- Both global-hotkey keystroke settings are cloud-synced SyncToCloud::Globally(RespectUserSyncSetting::Yes), private:false; keybindings.yaml is not. So cross-platform divergence is concentrated on the synced global hotkey. — `app/src/terminal/keys_settings.rs:14-50`
- DECISIVE CORRECTION to the brief: a mac cmd-based global hotkey synced to Linux is NOT 'unmatchable'. The winit backend maps keystroke.cmd -> Modifiers::SUPER (registers as Super-`), and displayed() renders cmd -> 'Logo' on non-mac (Logo == the Super key). So display and behavior already AGREE on Linux; there is no display-truthfulness gap. The real divergence is that cmd->Super differs from the keymap's cmd->ctrl (cmdorctrl) convention and Super-combos are often intercepted by the WM — a settings-resolution problem, not a keymap-editor display problem. — `crates/warpui/src/windowing/winit/delegate/global_hotkey.rs:99-110; crates/warpui_core/src/keymap.rs:1024-1029`
- The Keystroke STRUCT serde form is a live persisted/synced format with NO #[serde(default)]: the platform-native store (UserDefaults/registry) ALWAYS serializes the struct (settings/lib.rs:493-498), and cloud receives struct-form when FeatureFlag::SettingsFile is off (manager.rs:224-250). Adding a non-defaulted field to Keystroke (A6-Q3 option a) silently resets these synced/persisted settings to default. This hazard is unconditional for the platform-native store regardless of cloud rollout state. — `A6-Q4 (answers doc:2103-2148); crates/warpui_core/src/keymap.rs:320-354; crates/settings/src/manager.rs:224-250`
- Slash-command divergence is a THIRD construct, PerPlatformKeystroke{mac,linux_and_windows}, used only as COMPILE-TIME DEFAULTS collapsed at construction via OperatingSystem::get().is_mac() in FixedBinding::new_per_platform — NOT a user-persisted settings surface. User customizations of slash commands flow into keybindings.yaml like any other keymap binding. So the global hotkey is the ONLY genuinely separate synced/persisted keystroke surface. — `crates/warpui_core/src/keymap.rs:488-508; app/src/search/slash_command_menu/static_commands/bindings.rs:11-29`
- The global-hotkey settings store a SINGLE resolved Option<Keystroke> with no per-platform field, so a per-platform OVERRIDE (e.g. ctrl on Linux instead of Super) needs a new settings schema — but cross-platform DISPLAY of the one stored value is derivable from a displayed_for(target_os) helper with NO schema change. Inclusion in 'show both platforms' is therefore cheap; inclusion in 'edit/override per platform' is the expensive part. — `app/src/settings/mod.rs:334-338; crates/warpui_core/src/keymap.rs:998-1030`

**Options:**

- **Keymap-only (defer the settings surfaces) — as written in brief** _(low effort · easy)_ — R5 scope = Keystroke usage in the keymap + keybindings.yaml + matcher/displayed/validators only. Global-hotkey/QuakeMode and slash-command keystrokes keep current single-resolved behavior and are explicitly OUT of 'show/edit both platforms'. No serde constraint imposed on A6-Q3.
  - 👍 Smallest blast radius and fastest ship. keybindings.yaml is not synced, so if A6-Q3 also avoids touching the Keystroke struct, this slice is migration-free.
  - 👎 As WRITTEN it omits the load-bearing guard: if A6-Q3 picks the cmd_or_ctrl-on-Keystroke struct field (its option a), 'keymap-only scope' is a fiction — the struct change unavoidably hits the two synced + UserDefaults-persisted Option<Keystroke> settings and, without #[serde(default)], silently resets them. The defect is not the scope, it is the absence of the serde constraint. Option D fixes exactly this.
- **All Keystroke-backed surfaces (unified model + unified editor)** _(very-high effort · costly)_ — One platform-aware Keystroke model; the cross-platform editor shows AND edits keybindings.yaml, global-hotkey/QuakeMode, and slash-command bindings, all per-platform.
  - 👍 The only option that puts every keystroke a user sees, including the synced global hotkey, in one place with consistent per-platform editing — no second platform model maintained in parallel, and it directly enables a per-platform override (ctrl-on-Linux instead of Super) which is the actual global-hotkey fix users want.
  - 👎 Widens scope into settings serialization + a cloud-sync migration: the two Option<Keystroke> settings need a per-platform schema they lack today, plus migration of already-synced struct-form values. Slash-command per-platform bindings are compile-time defaults, so making them user-editable per-platform is a separate persistence project. Pulls settings into Axis 2's record schema. **Decision.** Decide whether R5's 'edit/show both platforms' cross-platform editor requires R6 (conflict detection) to take an explicit target-OS parameter — resolving and conflict-checking the inactive platform's bindings — as a hard prerequisite, or whether the editor ships with current-OS-only conflict feedback. Reframed by the attack into a two-part question: (a) the cheap design-now decision — does R6's API shape get a target_os parameter reserved at design time so it is not a retrofit; and (b) the expensive build decision — when (and whether) the inactive-platform conflict resolution is actually implemented, given it depends on storing both platform sides (A6-Q2), is Phase-2 work, and CANNOT be made fully honest by the param alone because some bindings are registered only on one platform.

**Stakes.** This sets the dependency spine, but the attack narrows where the real cost lives. Locking the param into R6's signature at design time is cheap and prevents an expensive retrofit later (R6 is still unbuilt, report:257). The expensive part — materializing the inactive side (A6-Q2 record schema, pulling in Axis 2) and, for TRUE honesty, de-gating platform-conditional registration — is Phase-2 and is NOT required to ship Phase 1 (report:244-251 contains no cross-platform editing). If we defer the param entirely and later add cross-platform editing, R6 must be re-cut to thread target_os: a real retrofit. If we over-build now, we pay for inactive-side storage and registration de-gating before measuring whether the conflict gap is even non-trivial. The truthfulness stake is real but bounded: even a fully built target_os ConflictMap leaves a residual gap (collisions against other-platform-only bindings like the mac-only character palette), so 'honest inactive conflicts' is achievable only for the shared binding set unless registration is also de-gated — a fact that must be stated honestly rather than claimed away. Critically: this is a Phase-2 implementation decision whose ONLY now-cost is a one-line API-shape commitment; it does not gate Phase 1.
