# Improved Keybindings — Spike Designs (adversarial)

**Date:** 2026-06-13
**Status:** Throwaway-build designs for the 14 `prototype-spike` design-readiness questions
**Companion to:** the [questions](./2026-06-13-improved-keybindings-design-readiness-questions.md), the [verified code answers](./2026-06-13-improved-keybindings-code-investigation-answers.md), and the [decision briefs](./2026-06-13-improved-keybindings-decision-briefs.md)

## Method

Each empirical unknown got a spike design (minimal throwaway build with named touch-points, a **quantified** success signal and kill signal, a time-box, and a *false-green* analysis), then a **red-team** whose first job was to construct the scenario where the spike passes but the real thing still fails — and to ask whether a cheaper non-build experiment (a grep, a type-check, a paper exercise) gets the same signal. A final pass sequenced them into a run portfolio.

Verdicts: **2** DESCOPED · **5** REDESIGNED · **6** SHARPENED · **1** MERGE/CUT

> A spike that gives a false green is worse than no spike. Each design states exactly what observation to trust — and what would make that observation a lie.

## Run portfolio

Front-load the four near-free settles (X7 cargo-check, A6-Q16 micro-bench, A1-Q6 settings read, A2-Q4 memo): they cost hours, outright cut two 1-2d frameworks (A1-Q6, A2-Q4), and hand the bigger builds their inputs — X7's leaf-Cow type and A6-Q16's ns/op table. Then run the de-risking builds in parallel across worktrees, because the only Axis-0 mutator among them is X9; the rest (A4-Q16 Helix selection, A5-Q5 conflict oracle, the merged A6-Q3/Q14/Q16 portability build, and the merged X12+A3-Q20 matcher-scan perf bench) share no state. X9 is the linchpin: its tombstone-short-circuit kernel tells you whether the expensive X1 needs a full LayeredKeymap store at all and fixes the match_custom leak (A3-Q5), while the perf bench adjudicates whether the R4 trie is a Phase-2 prerequisite or stays the deferred-optional item the roadmap promises. Only after X9/X6/X12 prove the pieces do you commit the 3-5d X1 integration capstone, now scoped to its two genuine legs (write-side invalidation fan-out + Unbound U-scaling) with the matcher-coupling leg cut to a grep. One hard gate the lead must enforce: capture X13's irreversible resolution snapshot in Wave 1 before X9 or any spike reorders bindings(), so every engine refactor diffs against a frozen golden. Net: most expensive build entered last and already de-risked, critical path X9->X6->X1, everything else parallelized around it, ~14 engineer-days, ~6.5-8 days wall-clock.

**Total time-box (run optimally):** ~14 engineer-days of actual work (down from ~25+ implied by the un-descoped designs, after the X12+A3-Q20 and A6-Q3/14/16 merges and the A1-Q6/A2-Q4/X7 cuts). Optimal wall-clock with 2-3 engineers is ~6.5-8 working days: Wave A ~0.5d (parallel hours-spikes), Wave B ~2d (parallel 1-2d builds across worktrees), Wave C ~1.5d (X6 ~1d + A3-Q4 ~0.5d), Wave D ~3-5d (X1 capstone). The critical path is X9 -> X6 -> X1 (~6.5d); A4-Q16/A5-Q5/A6-Q3/perf-bench all finish inside Wave B alongside it and never gate the path."

## Axis 1 — Config as portable, live data

### A1-Q6 — DESCOPED · time-box: hours

**Unknown.** After adopting the settings-proven pattern (write-free idempotent reload mirroring reload_all_public_settings at manager.rs:327, optionally plus a write-time semantic skip-if-unchanged mirroring write_to_preferences at lib.rs:500-515), is echo-SUPPRESSION (content-hash) even required for keybindings, or is echo-TOLERANCE sufficient? Two residual, non-loop concerns remain that content-hashing does NOT address and that must be settled elsewhere: (1) the non-atomic truncating write (File::create, file.rs:143) surfacing a torn/empty read whose None (keyboard.rs:128-138) would wipe all overrides — this is A1-Q5 (atomic temp+rename + split None into absent-vs-parse-error so None means 'keep last-good'); (2) whether the redundant echo reload can clobber an uncommitted in-app key-capture buffer — a UI state-ownership question answerable by tracing where capture state lives vs where set_custom_trigger applies, NOT by filesystem-timing. The loop-prevention question the spike centers on is no longer open: settings already proves a write-free idempotent reload terminates with zero self-writes.

**Hypothesis.** Echo-TOLERANCE wins; content-hash suppression is unnecessary scope. Make the keybindings reload write-free and idempotent (call set_custom_trigger/remove_custom_trigger only, never write_custom_keybinding), exactly as settings does — the echo reload then re-reads the file and re-applies identical in-memory state as a harmless no-op, with no loop (settings proves this in production over the same recursively-watched config_local_dir). External edits, coalesced or not, always survive because the reload always reads the final on-disk bytes and applies them; there is no guard to wrongly suppress them. Multi-process writers are handled the same way settings handles them: last-writer-wins + write-free reload. The two real residues are orthogonal to the loop: the torn-read wipe belongs to A1-Q5 (fixed by atomic temp+rename + None-keeps-last-good, eliminating the byte-identical-echo edge as a side effect), and the UI-capture clobber is a code-investigation of state ownership. If product later wants to suppress the redundant echo reload for performance, the cheapest correct mechanism is the settings write-time semantic skip-if-unchanged (lib.rs:500), not a reload-time canonical-map hash whose own PersistedTrigger normalization mismatch could silently break it.

_Why code can't settle it:_ Most of A1-Q6 IS now code-settleable and was before the build was scoped: reading settings (manager.rs:327 write-free reload, lib.rs:500 semantic skip-write, warp_managed_paths_watcher.rs:263 recursive config_local_dir watch, native.rs:130 the toml branch) proves an in-app writer already mutates its own watched file and breaks the loop without content-hashing. The ONLY part not settleable by reading code is one narrow empirical fact: whether the non-atomic truncate-then-BufWriter-flush of File::create actually surfaces an observable torn/empty read to a concurrent reader on this OS (so None→wipe is reachable in practice, not just in theory). That is a ~30-line repro, and it is A1-Q5's atomic-write question, not a 100-trial debounce-coalescing framework. The original spike's 'runtime timing of inotify + debouncer coalescing decides content-hash vs window' is moot once you don't suppress.

**The spike:** DESCOPED to hours. Drop the content-hash-vs-time-window 100-trial coalescing framework entirely. Replace with three cheap steps: (A) PAPER/GREP (free): document the settings precedent transfer — reload calls only set_custom_trigger/remove_custom_trigger (write-free, mirrors reload_all_public_settings), so the echo reload is a harmless idempotent no-op and external edits always survive; no guard needed. (B) MERGE-INTO-A1-Q5 torn-read repro (~hours): a ~30-line examples bin that drives the REAL save_custom_keybindings (truncating File::create + serde_yaml::to_writer over CustomKeybindings) in a tight loop on a temp file while a SECOND thread repeatedly calls read_custom_keybindings, asserting whether any None/empty/partial read is observable — the sole non-grep residue, owned by A1-Q5 to justify atomic temp+rename. (C) CODE-INVESTIGATION (~hours): trace where the in-app key-capture buffer lives vs where set_custom_trigger applies, to confirm an echo reload updates the global matcher only and cannot clobber an uncommitted capture (or identify the clobber path).

- _Touch points:_ `READ-ONLY precedent confirmation: crates/settings/src/manager.rs:327 (reload_all_public_settings — write-free idempotent reload, the actual loop-breaker), crates/settings/src/lib.rs:476-515 (write_to_preferences — write-time semantic skip-if-unchanged, the spurious-event reducer), app/src/warp_managed_paths_watcher.rs:263-269 (config_local_dir registered RECURSIVE — proves keybindings.yaml is already watched), app/src/user_config/native.rs:129-133 (settings branch that fires on the same watched toml)`, `torn-read repro (folds into A1-Q5): app/examples/keybindings_torn_read.rs driving app/src/keyboard.rs::save_custom_keybindings (:103-122) via app/src/util/file.rs::create_file (:143, truncating) against read_custom_keybindings (:128-138)`, `production target (unchanged): add a write-free branch to app/src/user_config/native.rs::handle_warp_managed_paths_event (:74-134) that, on a keybindings.yaml change, applies via set_custom_trigger only — hoisted to a mutable AppContext per A1-Q8 (init.rs subscriber), reconciling set/remove/revert per A1-Q4`, `UI-clobber trace: where write_custom_keybinding is called from the keybindings settings panel vs the global keystroke_matcher set_custom_trigger applies to`

(4) free 'no loop' from a stub that can't loop. The cleanest defense is to NOT build suppression at all: with write-free reload there is no guard to mis-tune, no coalesced edit to drop, and the torn-read is closed structurally by atomic write in A1-Q5.
