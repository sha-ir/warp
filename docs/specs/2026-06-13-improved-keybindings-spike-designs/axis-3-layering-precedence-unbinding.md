## Axis 3 — Layering, precedence & unbinding

**Unknown.** For the per-layer-chained layout (variant b only): (1) Can Keymap's bindings() chain the layer stores in precedence order while preserving today's EXACT lazy, zero-alloc .iter().rev().filter().map() shape AND keep the parallel shadow custom-action collections (fixed_custom_action_bindings/editable_custom_action_bindings, keymap.rs:36-37) coherent when update_custom_trigger's override moves into the user layer (A3-Q8)? Explicitly NOT the unknown: the (a)-vs-(b) latency ratio (that's a paper/type fact + A3-Q20), and the Unbound suppression primitive (A3-Q5/Q9/Q11).

**Hypothesis.** Variant (b) per-layer-chained is correct, but it wins on STRUCTURE not on a perf ratio. (b) preserves the exact lazy zero-alloc chain bindings() already has (keymap.rs:454-464), so precedence becomes "chain layers in order" with no new allocation and no hot-path cost change. (a) is rejected because emitting a single (layer,recency)-ordered stream over heterogeneous collections forces a per-call Vec collect + stable sort — a type/alloc fact, not a measured one. Everything else the spike claimed needed a build is actually settleable by reading: the lazy/zero-alloc (a)-vs-(b) verdict is a type fact (bindings() is already the proof-of-shape), and the "read-barrier dominates the hot path" premise is REFUTED by reading track_read's rendering_view gate (autotracking/mod.rs:272-287) against the non-render dispatch_keystroke caller (app.rs:2005-2039).

### A3-Q20 — SHARPENED · time-box: 1-2 days

**Unknown.** At warpui_core's real binding scale (N≈835: 384 FixedBinding::new + 451 EditableBinding::new static call sites, runtime bindings().len() of the same order), what is the --release wall-clock p99/max of (a) the current early-returning linear scan in push_keystroke (matcher.rs:324-338) and (b) the WORST-CASE post-Axis-3 layered resolver envelope — full candidate collect + sort by (layer,recency) + Unbound-suppression scan, no early return — on the worst-case keystroke (the most-shared chord leader that prefix-matches many bindings carrying the deepest real ContextPredicate trees, with no single-key completion so the full scan runs and pending is retained)? And does a PREBUILT first-keystroke index (HashMap<FirstKeystroke, Vec<idx>>, built once, only context-re-filtered per keystroke) cut p99 by >2x once that per-keystroke context re-filter is paid, or does the shared-leader candidate set collapse to ~the full set and erase the win? Decisive: is even the layered envelope p99 << the input-latency budget (target < ~100us, far under one 16ms frame) AND the prebuilt index shows no decisive >2x win — making the trie premature for Axis 3 PERF.

**Hypothesis.** A prebuilt first-keystroke index does NOT decisively beat the linear scan at this scale, and even the worst-case layered-resolver envelope stays far under the perceptibility budget, so the R4 per-context trie is premature optimization for Axis 3 perf. A scan over ~835 bindings where each ContextPredicate::eval is allocation-free HashSet::contains/HashMap::get (context.rs:101-119), each editable deref is one cheap with_cache TLS access (no dep-recording at dispatch since rendering_view is None, mod.rs:274), and the inner test is a length-1 Keystroke starts_with should land in low-tens of microseconds p99 (< 0.6% of a 16ms frame). On a shared chord leader the prebuilt index's candidate set approaches the full set, so its asymptotic win collapses while it adds traversal cost plus correctness risk against chord-reset (A3-Q7) and the unsettled ambiguity policy (A3-Q4). The layered envelope adds a per-keystroke collect+sort over the (small) context-matching candidate set plus an Unbound scan — a larger constant than the early-returning scan but still sub-100us at this N. Net: keep the O(n) scan for Axis 3, land the chord fix on the scan, defer the trie.

_Why code can't settle it:_ The trie-vs-scan crossover and the absolute wall-clock are not greppable: they depend on ContextPredicate::eval branch shapes, HashSet/HashMap probe costs, the length-1 starts_with compare, branch prediction, the per-deref with_cache thread-local UnsafeCell access on the Tracked<EditableBinding> path (which a synthetic FixedBinding bench skips), and the real predicate-depth distribution — none visible by reading. Whether a prebuilt index's per-keystroke context re-filter erases its asymptotic edge is an empirical crossover only a --release microbench at the real N resolves. The one thing code CAN bound is N: the 384+451=835 static call-site count caps runtime bindings() at low-thousands (call sites do not multiply into tens of thousands), which is 1-2 orders of magnitude below where a ~30ns/binding scan could approach 1ms — so the order-of-magnitude that the DECISION turns on is partly settleable on paper, but the layered-envelope constant factor and the index crossover are not.

**The spike:** Descoped throwaway: ONE #[ignore] timing test in the EXISTING matcher_tests.rs (no criterion, no benches/ dir, no separate app-dump binary). In --release it builds a synthetic Keymap through the REAL paths — register_fixed_bindings + register_editable_bindings so the Tracked<EditableBinding> deref / with_cache TLS tax is counted — at swept N in {500, 835, 2000, 5000} (835 bracketed by the static call-site count; 5000 as a margin stress). It measures push_keystroke p50/p99/max over >=200k iters via std::time::Instant on the WORST-CASE keystroke: the most-shared first keystroke that prefix-matches the largest set of multi-key bindings, where those matchers carry the DEEPEST ContextPredicate trees and there is NO single-key completion (so the scan runs full length and retains pending). It benches THREE resolvers on identical input: (a) the current early-returning scan; (b) a PREBUILT HashMap<FirstKeystroke,Vec<idx>> index built once at construction, traversed by pending.keystrokes then context_predicate.eval over only prefix candidates; (c) the WORST-CASE LAYERED ENVELOPE — each binding tagged (layer,recency), resolution = collect ALL prefix+context matches into a Vec, sort by (layer,recency), then scan an Unbound layer for suppression, NO early return. Predicate shapes/first-keystroke histogram are sampled from a multi-line-aware grep of the real id!/eq!/and!/or! args at the EditableBinding::new/FixedBinding::new call sites (cheaper than building the app). The synthetic generator reproduces that distribution and a worst-case shared-leader fan-out. The (a) and (b) numbers settle A3-Q20's literal trie-vs-scan; (c) is the false-green guard for the post-Axis-3 resolver.
