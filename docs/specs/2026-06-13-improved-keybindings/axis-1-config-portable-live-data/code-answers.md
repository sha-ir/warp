**Q.** On each reload, do we diff (apply only deltas vs the last-applied set) or nuke-and-reapply (remove_custom_trigger every previously-applied name, then re-set the whole file)?

**A.** Code facts decisively favor DIFF. Neither approach exists today (load runs once at launch, lib.rs:2557, and never removes; the file watcher in native.rs:74-134 has no keybindings.yaml branch at all); both require a NEW persistent last-applied map keyed by name, so diff is not more expensive in bookkeeping.

Why nuke-and-reapply is the more costly shape (the two concrete code costs):
1. pending.clear() on every mutator call. Matcher.set_custom_trigger (matcher.rs:137-141) and Matcher.remove_custom_trigger (matcher.rs:146-152) BOTH call self.pending.clear() (lines 138 and 150 — confirmed verbatim) before delegating to keymap.update_custom_trigger. pending is HashMap<EntityId, Pending> (matcher.rs:15) where Pending { keystrokes: Vec<Keystroke>, context } (matcher.rs:32-36) is the in-flight multi-keystroke chord buffer. So each call discards any partially-typed chord. Nuke-and-reapply makes N (remove) + M (set) calls per reload; diff makes only |delta| calls. More calls = strictly more chances to clobber the chord buffer. This is the decisive, directly-observable code cost.
2. Intra-reload revert window. update_custom_trigger(name, None) sets custom_trigger = None = revert to default (keymap.rs:422-433). Nuke-and-reapply first reverts every previously-applied name, then re-applies, so each binding passes through its default state mid-reload. Its observability depends on whether keystroke matching can interleave with the synchronous &mut AppContext reload handler (per A1-Q8 it generally cannot within one handler invocation), so this is mostly a state-model artifact while the pending.clear() drop is the concrete per-call harm — the answer correctly hedges this rather than overclaiming visible flicker.

Why diff is safe and cheap: update_custom_trigger is idempotent at the field level — it writes binding.custom_trigger for every binding whose name matches (keymap.rs:422-433). One precision worth recording (does NOT change the conclusion): the write iterates TWO collections, editable_custom_action_bindings (423-429) and editable_bindings (430-432), each filtered by `b.name == name`; it does not look up indices via editable_bindings_by_name (that index map, populated at 414-417, is consumed by get_binding_by_name at 379). The substance — re-setting a name to its current value changes nothing except the pending.clear() side effect, and the write hits all bindings with that name — is exactly right.

Bookkeeping required either way: The Matcher struct (matcher.rs:13-30) stores only pending, keymap, default_binding_validator, binding_validators, and two conversion fns — there is NO persistent set of applied names. The applied override lives only in EditableBinding.custom_trigger: Option<Trigger> (keymap.rs:300), and a name maps to a Vec of binding indices, so there is no clean name-keyed applied-map. (Nuance found: get_binding_by_name at keymap.rs:379 returns a lens exposing original_trigger: Option<&Trigger> which indirectly reveals whether a name is overridden — so "NO read-back API" is slightly strong — but it yields no applied-map and cannot distinguish file-applied overrides from in-app edits, so the conclusion that a new last_applied record is needed still holds.) Therefore both shapes need a new persistent last_applied: HashMap<String, AppliedKind> (Keystrokes | Empty | absent), seeded from the launch load, and diff is not the more expensive option.

Recommendation: DIFF, with a persistent last_applied seeded at launch. It avoids the intra-reload revert window for unchanged bindings, minimizes pending.clear() chord-buffer drops, exploits update_custom_trigger idempotency, and costs no more bookkeeping than nuke-and-reapply.
