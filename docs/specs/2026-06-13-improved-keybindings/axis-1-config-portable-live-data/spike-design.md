## Axis 1 — Config as portable, live data

### A1-Q6 — DESCOPED · time-box: hours

**Unknown.** After adopting the settings-proven pattern (write-free idempotent reload mirroring reload_all_public_settings at manager.rs:327, optionally plus a write-time semantic skip-if-unchanged mirroring write_to_preferences at lib.rs:500-515), is echo-SUPPRESSION (content-hash) even required for keybindings, or is echo-TOLERANCE sufficient? Two residual, non-loop concerns remain that content-hashing does NOT address and that must be settled elsewhere: (1) the non-atomic truncating write (File::create, file.rs:143) surfacing a torn/empty read whose None (keyboard.rs:128-138) would wipe all overrides — this is A1-Q5 (atomic temp+rename + split None into absent-vs-parse-error so None means 'keep last-good'); (2) whether the redundant echo reload can clobber an uncommitted in-app key-capture buffer — a UI state-ownership question answerable by tracing where capture state lives vs where set_custom_trigger applies, NOT by filesystem-timing. The loop-prevention question the spike centers on is no longer open: settings already proves a write-free idempotent reload terminates with zero self-writes.

**Hypothesis.** Echo-TOLERANCE wins; content-hash suppression is unnecessary scope. Make the keybindings reload write-free and idempotent (call set_custom_trigger/remove_custom_trigger only, never write_custom_keybinding), exactly as settings does — the echo reload then re-reads the file and re-applies identical in-memory state as a harmless no-op, with no loop (settings proves this in production over the same recursively-watched config_local_dir). External edits, coalesced or not, always survive because the reload always reads the final on-disk bytes and applies them; there is no guard to wrongly suppress them. Multi-process writers are handled the same way settings handles them: last-writer-wins + write-free reload. The two real residues are orthogonal to the loop: the torn-read wipe belongs to A1-Q5 (fixed by atomic temp+rename + None-keeps-last-good, eliminating the byte-identical-echo edge as a side effect), and the UI-capture clobber is a code-investigation of state ownership. If product later wants to suppress the redundant echo reload for performance, the cheapest correct mechanism is the settings write-time semantic skip-if-unchanged (lib.rs:500), not a reload-time canonical-map hash whose own PersistedTrigger normalization mismatch could silently break it.

_Why code can't settle it:_ Most of A1-Q6 IS now code-settleable and was before the build was scoped: reading settings (manager.rs:327 write-free reload, lib.rs:500 semantic skip-write, warp_managed_paths_watcher.rs:263 recursive config_local_dir watch, native.rs:130 the toml branch) proves an in-app writer already mutates its own watched file and breaks the loop without content-hashing. The ONLY part not settleable by reading code is one narrow empirical fact: whether the non-atomic truncate-then-BufWriter-flush of File::create actually surfaces an observable torn/empty read to a concurrent reader on this OS (so None→wipe is reachable in practice, not just in theory). That is a ~30-line repro, and it is A1-Q5's atomic-write question, not a 100-trial debounce-coalescing framework. The original spike's 'runtime timing of inotify + debouncer coalescing decides content-hash vs window' is moot once you don't suppress.

**The spike:** DESCOPED to hours. Drop the content-hash-vs-time-window 100-trial coalescing framework entirely. Replace with three cheap steps: (A) PAPER/GREP (free): document the settings precedent transfer — reload calls only set_custom_trigger/remove_custom_trigger (write-free, mirrors reload_all_public_settings), so the echo reload is a harmless idempotent no-op and external edits always survive; no guard needed. (B) MERGE-INTO-A1-Q5 torn-read repro (~hours): a ~30-line examples bin that drives the REAL save_custom_keybindings (truncating File::create + serde_yaml::to_writer over CustomKeybindings) in a tight loop on a temp file while a SECOND thread repeatedly calls read_custom_keybindings, asserting whether any None/empty/partial read is observable — the sole non-grep residue, owned by A1-Q5 to justify atomic temp+rename. (C) CODE-INVESTIGATION (~hours): trace where the in-app key-capture buffer lives vs where set_custom_trigger applies, to confirm an echo reload updates the global matcher only and cannot clobber an uncommitted capture (or identify the clobber path).

- _Touch points:_ `READ-ONLY precedent confirmation: crates/settings/src/manager.rs:327 (reload_all_public_settings — write-free idempotent reload, the actual loop-breaker), crates/settings/src/lib.rs:476-515 (write_to_preferences — write-time semantic skip-if-unchanged, the spurious-event reducer), app/src/warp_managed_paths_watcher.rs:263-269 (config_local_dir registered RECURSIVE — proves keybindings.yaml is already watched), app/src/user_config/native.rs:129-133 (settings branch that fires on the same watched toml)`, `torn-read repro (folds into A1-Q5): app/examples/keybindings_torn_read.rs driving app/src/keyboard.rs::save_custom_keybindings (:103-122) via app/src/util/file.rs::create_file (:143, truncating) against read_custom_keybindings (:128-138)`, `production target (unchanged): add a write-free branch to app/src/user_config/native.rs::handle_warp_managed_paths_event (:74-134) that, on a keybindings.yaml change, applies via set_custom_trigger only — hoisted to a mutable AppContext per A1-Q8 (init.rs subscriber), reconciling set/remove/revert per A1-Q4`, `UI-clobber trace: where write_custom_keybinding is called from the keybindings settings panel vs the global keystroke_matcher set_custom_trigger applies to`
- _Harness:_ (A) is a paper finding, no run. (B) Manual: cargo run -p app --example keybindings_torn_read prints count of torn/empty reads observed over N self-writes; >=1 ⇒ atomic temp+rename required (feed A1-Q5); 0 over many ⇒ atomic write is defensive-only. (C) is grep+read, no run. NO debounce framework, NO content-hash guard, NO strawman window guard, NO 100-trial concurrent-coalescing pass.

- ✅ **Success:** (1) PRECEDENT TRANSFER CONFIRMED (free): settings demonstrably breaks the identical loop (in-app writer over a recursively-watched config dir) with a write-free idempotent reload and no content-hash — so the keybindings reload designed to call only set_custom_trigger terminates with zero self-writes BY CONSTRUCTION, and external edits survive because the reload always reads final bytes. This is asserted by construction + analogy, not measured. (2) TORN-READ repro yields a clear bit: the concurrent reader observes >=1 None/empty/partial read across N real save_custom_keybindings calls ⇒ atomic temp+rename is REQUIRED (hand to A1-Q5); 0 across many trials ⇒ atomic write is defensive-only. (3) UI-clobber trace shows the reload mutates the global matcher, not the capture widget's pending buffer ⇒ no self-clobber of uncommitted capture (or it names the exact clobber path). Headline: A1-Q6 resolves to 'echo-TOLERANCE via write-free idempotent reload (settings pattern), suppression NOT required' — no 100/100 coalescing threshold needed because suppression is cut.
- 🛑 **Kill:** (1) The write-free idempotent reload does NOT terminate — i.e., applying the loaded map via set_custom_trigger somehow re-persists to disk and re-fires the watcher. This is essentially pre-killed: settings proves a write-free reload over the same watched dir terminates in production, and the design forbids the reload path from ever calling write_custom_keybinding. If it fired, kill any apply path that re-persists. (2) The torn-read repro shows the wipe is reachable AND atomic temp+rename does NOT close it (e.g., rename still races the watcher) — would re-open a genuine empirical unknown, but it is A1-Q5's, not A1-Q6's. (3) The UI-trace finds the reload writes into the same buffer the capture widget reads from — a real self-clobber that write-free reload alone doesn't fix (would require a 'don't apply while a capture is open' interlock, still not content-hash). None of these resurrect the content-hash-vs-window contest.
- ⚠️ **False-green risk:** The dominant false green is INVERTED from the spike's framing and worse: the spike can GREEN its content-hash design and thereby 'prove' suppression is needed and correct, shipping per-write canonical-map hashing + last_written_hash bookkeeping + a suppression branch — when the simpler, production-proven design (write-free idempotent reload, already running in settings over the same recursively-watched config_local_dir) needs none of it. That manufactures confidence in unnecessary, higher-maintenance machinery whose own suppression logic can introduce the very external-edit-drop bug it set out to avoid: e.g., a canonicalization mismatch between PersistedTrigger write-normalization (Keystroke::normalized, keyboard.rs:180) and read-parse silently turns the guard into apply-everything (a permanent no-op) or, worse, drop-something. The spike never tests against the write-free baseline, so it cannot discover that its whole premise is moot. Secondary false greens, which only bite ANYONE who still builds suppression: (1) torn-read via non-atomic write (S5) — really A1-Q5; a green that writes-then-reads at rest never hits it. (2) debounce double-merge (BulkFilesystemWatcher dedup + WarpManagedPathsWatcher debounce) masking the window guard's failure. (3) serialized-not-concurrent harness making the kill scenario a no-op. (4) free 'no loop' from a stub that can't loop. The cleanest defense is to NOT build suppression at all: with write-free reload there is no guard to mis-tune, no coalesced edit to drop, and the torn-read is closed structurally by atomic write in A1-Q5.
- 💡 _Cheaper alternative:_ YES — most of A1-Q6 needs no build. Reading settings settles the loop question: warp_managed_paths_watcher.rs:263-269 (config_local_dir is RECURSIVE, so keybindings.yaml is already watched), native.rs:129-133 (settings reacts to its own watched toml), manager.rs:315-327 (reload_all_public_settings is write-free and idempotent — the actual loop-breaker, comment: 'avoiding write-back loops with the file watcher'), and lib.rs:500-515 (write_to_preferences semantic skip-if-unchanged — the spurious-event reducer). This proves an in-app writer ALREADY mutates its own watched file and avoids a loop without any content-hash. The only thing left that a grep can't settle — does the non-atomic truncating write surface a torn/empty read — is a ~30-line repro that belongs to A1-Q5. So: cut the 1-2 day framework; do the free settings read + the hours-long torn-read repro under A1-Q5.
- _Keep vs throw:_ KEEP: (a) the write-free idempotent reload design — keybindings reload calls only set_custom_trigger/remove_custom_trigger, mirroring reload_all_public_settings (manager.rs:327); promote into the new branch in handle_warp_managed_paths_event (native.rs:74-134). (b) the torn-read repro and its scenario — promote into A1-Q5 as the atomic-write justification. (c) optionally, a write-time semantic skip-if-unchanged mirroring write_to_preferences (lib.rs:500) to suppress spurious echo reloads cheaply IF a perf/flicker need is shown. THROW: the entire content-hash canonical-map machinery, last_written_canonical_hash bookkeeping, the strawman time-window/dirty-flag guard, the standalone notify-debouncer scaffolding, the BulkFilesystemWatcher S2 pass, and the 100-trial concurrent-coalescing framework — they solve echo-SUPPRESSION, a problem the recommended echo-TOLERANCE design does not have.
- _Unblocks:_ A1-Q6 resolves to 'echo-tolerance via write-free idempotent reload (settings pattern at manager.rs:327), not echo-suppression / content-hash'. Hard-couples the only empirical residue (torn-read wipe) to A1-Q5 (atomic temp+rename + split None into absent vs parse-error). Constrains A1-Q4 (the write-free reload must distinguish set / remove / revert-to-default to be idempotent). Confirms A1-Q8 (the reload host needs only a mutable AppContext to call set_custom_trigger; it must be write-free). Lets the decision-brief 'naive watcher-only over the flat map' option ship as a small correct add (a write-free branch) rather than a content-hash subsystem. Unblocks Axis-4 Step-D (live-aliasing rewrite), which the briefs gate on A1-Q6.
- _Residual risk:_ (1) Loop-safety transfers from settings, but torn-read safety may NOT: settings' reload_from_disk may hold last-good on parse error, whereas keybindings' read_custom_keybindings returns None on BOTH absent-file and parse-error (keyboard.rs:128-138), so the wipe gap is keybindings-specific and must be closed in A1-Q5 (atomic temp+rename + split None semantics). Verify settings' actual parse-error behavior before claiming full transfer. (2) The UI-capture-clobber answer is asserted-not-proven here; it needs the code-investigation trace of where the panel's pending buffer lives. (3) If product later wants to suppress the redundant echo reload purely for performance / to avoid a visible re-render flicker, that is a real (if minor) open item — but the cheapest correct mechanism is the settings write-time semantic skip-if-unchanged (lib.rs:500), not a reload-time content-hash, and even that is an optimization, not correctness. (4) Multi-process (two Warp instances) is handled exactly as settings handles it (last-writer-wins + write-free reload); content-hash would not improve it and could wrongly suppress process B's byte-identical write — but that suppression is a provable no-op anyway.
- _Red-team:_ Five hits, all grounded in code I read: (1) FALSE PREMISE — the spike's load-bearing claim "no precedent for a writer that mutates its own watched file (settings never writes back)" is wrong. config_local_dir is registered RECURSIVE (warp_managed_paths_watcher.rs:263-269) and keybinding_file_path()=config_local_dir/keybindings.yaml (keyboard.rs:96), so the file is ALREADY watched; user_preferences.toml lives under the SAME recursive watch and the in-app settings UI writes it via write_to_preferences (lib.rs:476). Settings IS exactly an in-app writer mutating its own watched file. (2) STRAWMAN A/B — the spike pits content-hash vs time-window but OMITS the actual production-proven winner: a write-free idempotent reload. Settings breaks the loop at manager.rs:327 (reload_all_public_settings loads into memory without writing back; comment: 'avoiding write-back loops with the file watcher'), NOT via content-hashing. So the headline 'content-hash WINS' is a contest against a guard nobody needs to pick. (3) SELF-INFLICTED KILL SCENARIO — S2 (a coalesced external edit silently dropped by suppression) only EXISTS if you choose to suppress. With write-free reload there is nothing to suppress: every reload re-reads the FINAL on-disk bytes and re-applies them, so external edits always survive by construction. The 100-trial concurrent-coalescing framework tests a problem the recommended design doesn't have. (4) PROXY MISMATCH — A1-Q6's named self-clobber risk is 'a reload landing mid-UI-edit clobbers unsaved CAPTURE state', but the spike only measures the applied keymap, never the in-flight capture widget. It measures the wrong state. (5) RESIDUE IS A1-Q5's — the only genuinely non-grep-able thing left (does the non-atomic truncating File::create surface a torn/empty read → None → wipe) is the A1-Q5 atomic-write question, and the spike's own kill_signal #3 admits A1-Q6 'cannot be settled independently of A1-Q5'. That residue is a ~30-line repro, not a 1-2 day framework.
