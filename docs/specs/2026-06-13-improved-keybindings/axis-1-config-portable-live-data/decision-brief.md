## Axis 1 — Config as portable, live data

### A1-Q1 — HARDENED · _product_ · owner: Product DRI for the keybindings initiative (owner of the end-goals/roadmap docs), who makes the scope call with the keybindings tech lead for sizing. The question is tagged user-product-decision, so product holds the ruling; engineering supplies the effort estimate. The tech lead additionally owns recording the Axis-2 duplex-reader (A1-Q12) acceptance criterion so deferral carries no migration debt.

**Decision.** Whether the rich context/platform-scoped persisted schema (R3b: flat HashMap<name, PersistedTrigger> becoming records of {name, trigger, optional context, optional platform}) is in scope for Axis 1, or whether Axis 1 ships ONLY the hot-reload watcher + reset/last-applied bookkeeping over today's flat map and defers R3b to Axis 2. Re-grounding sharpens the ruling: the schema-dependent question chain (per-context round-trip, cross-platform import, unknown-name migration, schema back-compat) is genuinely Axis-2 work, AND R3b alone cannot deliver per-context capability without a separate keymap engine change, AND the flat back-compat that deferral allegedly risks is already owed to every existing customizer regardless. So the call is not a close scope judgment hedged by serde tricks — it is a clear defer, with the only residual product input being whether cross-OS shared-config import is a first-release promise (a narrow R5 slice, not R3b).

**Stakes.** Sizes the whole axis. Watcher-only over the flat map is a low-effort win delivering the "config as portable, live data" outcome (instant apply of a shareable file with correct revert/unbind). R3b-in-scope turns it into a multi-week schema + parser + migration + back-compat project AND, because per-context overrides also require a keymap engine change (update_custom_trigger is name-keyed, keymap.rs:422-433), would ship a rich format with no engine consumer. Mis-scoping over-builds (slips the live-data win on a speculative, currently-unusable schema) far more than it under-builds: the under-build risk the brief feared (a breaking migration of interim hand-authored files) is largely illusory because the in-app UI already writes the same flat format to disk today (keyboard.rs:64-75), so Axis 2 owes a flat back-compat reader to the entire existing user base whether or not the watcher ships. The decision is surfaced now because the docs contradict each other: end-goals lists R3b as an Axis-1 leaf (L52-53) while the report roadmap (section 7) and dependency spine (L117, "no schema/engine change") put R3b in Phase 2. That contradiction needs a one-line doc correction now; the engineering can proceed against the flat map immediately either way.
