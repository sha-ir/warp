### A6-Q16 — REDESIGNED · time-box: hours

**Unknown.** Once bindings are stored UNRESOLVED (a {mac,other} pair, or a cmdorctrl token, instead of a parse-time-resolved Keystroke), must keystroke resolution happen inline per-binding during the O(n) push_keystroke scan, or once at registration into a current-OS resolved cache? Reframed after attack: this is NOT a single yes/no — it is a PER-REPRESENTATION question feeding A6-Q3, and the operative axis is correctness/complexity, not latency. For each representation A6-Q3 is actually choosing among, two facts: (a) is the inline resolution op allocation-free O(1) bool/branch work (pair side-select; cmdorctrl field-wise) whose isolated ns/op is a small single-digit fraction of the per-binding floor (predicate eval + Tracked Deref thread-local + BindingLens construction); and (b) does choosing a cache introduce an invalidation surface that must be hand-wired across every mutation path. The decision: inline unless a representation forces per-compare re-parse/allocation that cannot be rewritten field-wise. Perf only rules out a pathological representation; it does not, by itself, justify a cache.

**Hypothesis.** Inline resolution is free for every realistic unresolved representation, AND it eliminates an entire bug class (cache staleness), so NO resolve-at-registration cache is needed. The hot dispatch path uses the compile-time current OS (OperatingSystem::get cfg_if → constant the optimizer hoists), so side-selection is a branch returning &Vec<Keystroke> with no allocation and no re-parse, then the same derived-PartialEq starts_with as today. For a cmdorctrl-bool-on-flat-Keystroke form, the honest implementation resolves field-wise (a couple of bools + a branch, key:String untouched) — also free; the String-cloning per-compare form is a strawman no one would ship. The per-binding cost is dominated by context_predicate.eval PLUS the already-present Tracked Deref thread-local borrow and BindingLens construction, against which resolution is noise. Decisive (non-perf) reason to prefer inline: the unresolved form is the single source of truth recomputed each scan, so there is no parallel resolved copy to invalidate across update_custom_trigger / set_custom_trigger / remove_custom_trigger / hot-reload / register re-registration / pending.clear — Tracked is reactive-only (track_update queues view invalidations, it is NOT a memo cache), so a cache would need its own correct hand-wired invalidation on every path, which is the actual risk. The ONLY representation that could flip this is one that stores a token requiring re-parse (or a value requiring reconstruction) per compare that cannot be made field-wise — and that is the kill case A6-Q3 should be steered away from.
