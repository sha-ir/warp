## Axis 2 — Scope & context control

### A2-Q1 — HARDENED · _product_ · owner: Keybindings-initiative product owner (PM) decides scope and the user-facing public names, jointly with the warpui_core keymap/engine owner who owns the intern+validation table, the alias-indirection mapping, and the naming-convention RFC. NEW: the Axis-3 owner must co-sign on sequencing, because whether a published vocabulary delivers user value depends on Axis-3 Fixed-remappability and on the per-binding override path (A2-Q11) landing. The docs/catalog owner (Axis-5 R9) is a consumer, not a decider. Not a pure-eng call: it defines the public config API and the names users memorize.

**Decision.** Define the stable, documented, versioned set of context atoms that user-authored keybinding predicates may reference, and fence off the internal flags (the ~454 auto-inserted ui_name() identifiers, transient UI state, test-only literals) that users must not depend on. REFINEMENT from the attack: the published vocabulary should be a curated PUBLIC ALIAS layer (an indirection table mapping a stable public name to one-or-more internal flags), not a bare allowlist of internal names — so internal refactors (the exact concern in the stakes paragraph) update one table entry instead of breaking every user config, and the existing duplicate/inconsistent names collapse to a single public alias. Do the partition + naming RFC NOW (cheap, and the single source of truth for the parser, the A2-Q10 validator, and the Axis-5 R9 catalog), but PUBLISH/FREEZE names incrementally — only once a context-aware override path exists to consume them — so no name becomes a one-way commitment before users can depend on it. Minimal-first set scoped to what is deliverable in Phase 2: cross-view scoping (Terminal vs code/editor vs AI-input). Vim-mode atoms explicitly DEFERRED to the Axis-3 release because the canonical Vim forks are FixedBindings the override path cannot reach today.

**Stakes.** Context-scoped bindings are the headline value of Axis 2, but a predicate is only durable if the flags it names are durable AND only useful if an override path can act on them. Today the namespace is undifferentiated: ~60 inconsistent product set.insert(\"...\") literals PLUS ~454 auto-inserted ui_name() Rust-type identifiers, stored as &'static str with no parser and no public/internal distinction. Exposing this raw makes every user predicate an unversioned coupling to internal names that change on routine refactors — positive atoms fail closed (config silently breaks), negative atoms fail open (bindings leak into wrong views), with none of the engine's positive-gate discipline available to a config author. This is genuinely the foundational API-surface decision and freezing an internal name is a one-way trap. BUT the attack reveals the urgency is lower than the brief implies: the vocabulary delivers no user-visible value on its own. The whole override write path is name-only (set_custom_trigger/update_custom_trigger carry no context), so a scoped override cannot even be created; and the flagship motivating cases (Vim enter/backspace/tab forks) are FixedBindings unreachable without Axis 3. So the real stake is 'design the durable surface and avoid the trap now, but do not pay the freeze cost before a consumer exists.'

### A2-Q2 — HARDENED · _cross-team_ · owner: Cross-team. The engine tech lead (owner of crates/warpui_core/keymap) decides the engine answer — (name x context). The config-schema owner (app/src/keyboard.rs load/write path + user_config) co-signs and OWNS the new pieces: the platform? load-filter and the write-preservation of non-host records. The R5 / cross-platform-foundation owner is explicitly OFF the critical path for file portability — R5 owns only the in-app cross-platform EDITOR (showing/editing the other OS's binding). Product owns the gating input: whether a single per-OS-divergent keybindings.yaml synced across machines is in scope for release 1.

**Decision.** Split the question into the two layers the brief merged. (1) At the ENGINE layer, a context-scoped override is identified by (name x context); platform can never be an in-process disambiguator because every per-platform path — FixedBinding::new_per_platform AND the override-relevant editable builders — collapses to the host keystroke at registration, and update_custom_trigger filters by name alone over host bindings. Decide this now. (2) At the FILE layer, is platform? (a) absent/fully deferred to R5, (b) part of an engine-honored (name x context x platform) identity, or (c) a RESERVED optional load-FILTER selector (host-match-or-skip) defined now but wired only on a product greenlight for synced cross-OS files? Co-committed with the A2-Q3 schema shape (record list with optional fields).

**Stakes.** A2-Q3 forces a one-time fork from today's flat name->trigger map to a scoped-override record; platform rides the same record and the same migration, so its treatment must be co-committed. Both error directions are costly: omit any platform provision and a later need re-opens the migration; make platform an engine-honored identity dimension and you ship config the host-only engine cannot exercise. The brief's framing hid a conflation that changes the cost calculus: making a synced keybindings.yaml portable across OSes does NOT require the R5 engine refactor (only an in-app cross-platform EDITOR does, per L7/report:132,146,231); a file-level load filter suffices because each build already applies only host-resolved keystrokes. So the real lever is the FILE/loader, not the engine, and the decision pivots on a product call about whether synced cross-OS files are in scope for release 1.

**Options:**

**Options:**

- **A. File-only; UI made scope-safe but scoped rows read-only (defer the editor)** _(med effort · easy)_ — Engine + file get context scoping (Axis 2 core). No predicate editor in the UI. Two mandatory UI changes: change row dedup from name+description to name+context so each scoped registration gets its own visible row, and make the save path lossless so it preserves file-authored scoped entries instead of clobbering them. Scoped rows render read-only with an 'edit in config file' affordance. Requires exposing EditableBindingLens.context to the app crate (private today, keymap.rs:311) and a schema that carries context for lossless round-trip, plus R6.
  - 👍 Smallest cut that does not regress and is the non-negotiable substrate under every other option. It needs NO write-side serializer (the UI never authors context, only preserves file-authored entries) and NO parser, so it de-risks the release and lets Axis 2's engine land now. Power users who scope already hand-edit YAML, so a truthful read-only-with-link row serves them. Fully reversible: the editor can be added later.
  - 👎 A read-only row a GUI user cannot edit in place is only a half-truth versus the North Star: the 80% case (rebind X only in the terminal, where X already has scoped registrations) stays visible but uneditable for GUI-only users, hurting discoverability and risking calcification as permanent debt. It is NOT a do-nothing option: leaving today's name+description dedup and name-only save in place would actively clobber scoped overrides, so the dedup change, lossless save, context exposure, and R6 are all unavoidable even here.
- **B. Curated global preset context dropdown** _(high effort · costly)_ — Add a per-row dropdown exposing a small curated set of named contexts (Global/Terminal/Code editor/Vim/...) that map to compile-time predicates; row dedup becomes name+context. Unlisted/arbitrary predicates authored in the file fall back to A's read-only row.
  - 👍 If a faithful small vocabulary existed, this would give GUI users a real in-UI editor while sidestepping a free-form grammar and arbitrary-string interning, and align with the curated-vocabulary direction A2-Q7 points toward.
  - 👎 The premise fails against the data: ~94 distinct, mostly-composite real predicates (IME/flags/drag/vim-submodes) mean there is no faithful small global set, and the contexts available for an action are per-registration, not global, so a label like 'Terminal' cannot deterministically pick among composite terminal registrations. - **C. Full free-form predicate editor (UI parity with the file)** _(very-high effort · one-way)_ — A predicate-expression editor per row (&&/||/!/==/!=) round-tripping to/from the file. Requires the full A2-Q15 Display serializer + A2-Q19 FromStr parser, &'static interning/Box::leak, Just(false) canonicalization, and context-aware conflict detection.
  - 👍 True parity: the UI is exactly as expressive as the file, fully satisfying 'the UI is the truth' with no second-class rows and one coherent model.
  - 👎 Largest, riskiest surface and worst cost/benefit. Builds the entire serializer+parser+interning+grammar stack from scratch (none exists, context.rs:9-18) plus a boolean-expression authoring UX that is a usability minefield. Once users author arbitrary predicates that serialize to file, the grammar becomes a permanent public contract you must parse forever (one-way). &'static storage forces Box::leak/interning of unbounded user input, a slow memory-leak vector. Massive over-build for a capability almost no GUI user needs.
- **D. Editable scoped rows derived from existing registrations (serialize-and-match; no parser, no preset taxonomy, no inject path)** _(high effort · costly)_ ✅ **recommended** — Build on A's substrate, but make each un-collapsed scoped row EDITABLE in place rather than read-only. The context is shown as a derived, humanized read-only LABEL (no predicate authoring). In-session, the edit applies via a new override path keyed by the row's BindingId (resolving A2-Q3 as: BindingId in-memory). On disk, persist by (name + Display-serialized predicate); on load, Display-serialize each registered binding's predicate and string-MATCH to locate the target binding, then apply. This needs only the write-side Display serializer (A2-Q15): NO read-side parser (A2-Q19 avoided), NO interning/Box::leak (a new 'static predicate is never built from file text), and NO inject path (only contexts that already exist are editable).
  - 👍 Best cost/faithfulness point for Phase 1. It serves the real 80% case (rebind X only in the terminal) wherever X already has scoped registrations, which the data shows is the common shape: same name registered across views with different predicates, collapsed today. It offers EXACTLY the contexts that exist, eliminating B's taxonomy guesswork, the preset->registration matching ambiguity, the power-user cliff, and the inject engine path. Strictly cheaper than B (no parser, no interning, no taxonomy, no inject) yet more faithful to the North Star (every existing scoped binding gets its own truthful, editable row). The serialize-and-match trick dissolves the parser/interning problem that dominates C and partially burdens B.
  - 👎 Does not let a GUI user CREATE a scoping that does not already exist in code (e.g., fork a globally-registered action to terminal-only): that still routes to YAML or a later inject capability (A2-Q4). The Display serialization format becomes a contract for orphan-avoidance: if a binding's predicate changes in code, previously-persisted overrides for it are silently orphaned until re-saved (acceptable, same inert-override semantics as an unregistered action today, and migratable on load while the binding still exists). Still requires A's substrate + R6 + exposing the context field cross-crate. Humanizing composite predicates into readable labels (e.g. Terminal&!IMEOpen&LongRunningCommand) needs a small design pass.
