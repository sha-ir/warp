### A2-Q7 — CONFIRMED · confidence: high

**Q.** Do config-authored predicates evaluate against a SINGLE per-view Context or a merged chain context? contexts_from_responder_chain (core/app.rs:1839-1864) builds a Vec<Context> with no merge loop (Context::extend at context.rs:90-97 is unused); dispatch_keystroke/push_keystroke (app.rs:2005-2041; matcher.rs:307-346) eval each predicate against one per-view ctx. The architecture report (line 32) wrongly claims context is "merged up the responder chain." Do we (a) keep per-view eval and forbid cross-level ANDs in the documented vocabulary, or (b) build a merged-context variant for predicate eval?

**A.** Per-view, decisively. Predicates (config-authored or compiled) are evaluated against exactly ONE view's Context at a time. The engine never merges the responder chain: contexts_from_responder_chain builds a Vec<Context> by pushing each view's keymap_context separately (only IMEOpen is inserted), and every matcher entry point evals binding.context_predicate.eval(ctx) against a single ctx. The keymap Context::extend exists but has no callers on a keymap Context. The architecture report's "merged up the responder chain" claim (line 32) is wrong.
